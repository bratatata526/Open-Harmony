### 1.2 ✅ 已确认：三块 MH-Sensor-Series 外接传感器模块（实拍）

**重要**：这三块模块用的是**同一款 PCB 模板**（丝印都是 `MH-Sensor-Series / VCC GND DO AO` + `LM393` + 蓝色 3362 电位器），**只有顶部的敏感元件不同**。所以**不能靠 PCB 外观区分型号，必须靠"给它一个物理激励，看 AO 是否响应"来识别**。

| 照片 | 顶部敏感元件（外观） | 极可能的型号 | 判定依据 |
|---|---|---|---|
| IMG_9013（正面）<br>IMG_9014（背面） | **白色圆片，带两根引脚**，元件位于板子底边外沿 | **光敏电阻（LDR/GL5528）光照模块** | 白色圆片 + 两根引脚 = 典型 LDR 封装；PCB 上 `R3` 位置与之串联构成分压 |
| IMG_9006 / 9007 | **不透明黑色半球 + 黑色保护套**，元件在板子顶端 | **红外/火焰 或 光敏**（两者 PCB 相同，外观接近） | LM393 + 电位器 + 黑色遮光罩结构，是火焰模块与光敏模块的共有特征，**需实测区分** |
| IMG_9012 | **黑色元件 + 蓝色元件并排**（像两颗 LED 并立） | **火焰传感器模块**（黑色=红外接收管，蓝色=指示/发射管） | 这是红外火焰探测模块的经典双元件布局 |

> ⚠️ **不要靠猜**：以上是"最可能"，而 MH-Sensor-Series 是万能模板板，光敏/火焰/湿度/霍尔都用它。**照 §1.2.1 花 10 分钟实测确认**，把结论填进 §5 的确认表。

#### 1.2.1 模块识别流程（不接任何单片机，10 分钟）

```
① VCC → 3.3V，GND → GND（用面包板电源或 STM32 的 3V3 引脚）
② 万用表直流电压档，红表笔接 AO，黑表笔接 GND
③ 依次施加下面三种激励，记录 AO 电压变化：
```

| 施加的激励 | 如果 AO 明显变化（> 0.5V） | 结论 |
|---|---|---|
| 手机手电筒照 / 用手完全遮住 | 变化 ✅ | **光敏（光照）模块** → 接 STM32 ADC |
| **不点火**，把打火机的出气口靠近元件；或用遥控器红外发射头对着它按键 | 变化 ✅ | **火焰 / 红外模块** → 可做"明火报警"演示 |
| 对着元件哈气，或靠近热水杯的蒸汽 | 变化 ✅ | **湿度模块** → 可做湿度数据源 |
| 三种都没反应 | ❌ | 检查 VCC 是否有电；或该模块需 5V 供电（此时**不要接 STM32 的 ADC**，需分压后再接） |

补充验证（同时确认模块本身完好）：
- 旋转蓝色电位器，用万用表看 **DO** 引脚电平是否在某个位置翻转 → 翻转即证明 LM393 比较器工作正常；
- 记下暗/亮两种状态下的 AO 电压，写进 §5 确认表。

#### 1.2.2 引脚定义（4 针，丝印已确认，注意顺序两种都有）

```
丝印 A（IMG_9007 / 9012 背面）：  VCC  GND  DO  AO
丝印 B（IMG_9013 背面）：         VCC  GND  DO  AO
两种模块丝印顺序一致，但【正面看是反的】，接线前先按丝印确认。

  VCC ── 电源：⚠️ 必须 3.3V，绝不可 5V（见下方说明）
  GND ── 地
  DO  ── 数字输出（LM393 比较结果）→ 可选接 STM32 普通 GPIO
  AO  ── 模拟输出（分压电压）      → 接 STM32 ADC 通道
```

> ⚠️ **电压要求必须实测确认**：LM393 是**开集输出**，模块通常标注 3.3V–5V 兼容，但**分压支路（AO）的满量程电压等于 VCC**。
> - 若 VCC 接 **5V** → AO 可能输出 5V，**超过 STM32 的 ADC 输入耐压**（STM32 ADC 引脚为 3.3V 域，5V 会损坏引脚）。
> - **正确做法**：VCC 接 **3.3V**，AO 直接接 STM32 ADC 引脚，无需分压。
> - **验证方法**：用万用表量 AO 对 GND 的电压，两种激励状态下都应 ≤ 3.3V。

### 1.2.3 ★★ 结论：光敏模块的 AO 无法接到 FS-Hi3861（原理图已确认）

**先看板子的扩展口定义**（来自 `doc/board/FS-Hi3861-V4.2.pdf` 第 6 页 `06_Interface`，原理图就在仓库里）：

| 扩展口 | RJ12 位号 | 暴露的信号 |
|---|---|---|
| 接口1 SPI | J2 | GND, SPI_CS, SPI_CLK, SPI_RXD, SPI_TXD, VCC |
| 接口2 I2C | J3 | GND, **IIC_SCL, IIC_SDA**, IIC_INT |
| 接口3 UART | J4 | GND, USART2_RXD, USART2_TXD, KEY |
| 接口4 GPIO | J5 | GND, **A1, A2, D0, D4** |

**关键发现**：接口4 名义上叫 "GPIO"，但暴露的是 **PCF8574 的引脚**（`A1/A2/D0/D4`）。
PCF8574 是一颗 **I2C 数字 IO 扩展芯片**，驱动代码 `hal_bsp_pcf8574.c` 证实其用途：

```c
tmp_io.bit.p0 = 1;  // P0 → 风扇
tmp_io.bit.p1 = 0;  // P1 → 蜂鸣器（低电平有效）
tmp_io.bit.p2 = 0;  // P2 → LED
tmp_io.bit.p5 = 1;  // P5 → D2
```

**PCF8574 只能读写数字电平，不能读模拟电压。**

同时，原理图第 4 页显示板载外设**全部挂在 I2C 总线上**：

| 器件 | I2C 地址 | 用途 |
|---|---|---|
| SHT20 | 0x40 | 空气温湿度 |
| AP3216C | 0x1E | 环境光 / 接近 / 红外 |
| AW2013 | 0x55 | RGB 三色灯 |
| NFC | — | 近场通讯 |
| OLED | — | 0.96" 显示 |
| PCF8574 | — | 风扇 / 蜂鸣器 / 按键（数字 IO 扩展） |

**所以：这块板子没有把任何 ADC 引脚引出来。**
光敏电阻模块的 `AO`（分压模拟输出）**物理上无处可接**，`hi_adc_read()` 无引脚可用。

> **另一个附带发现**：接口1 SPI（J2）与接口3 UART（J4）暴露的信号在板内是**并联**的
> （`SPI_RXD` = `USART2_TXD`、`SPI_TXD` = `USART2_RXD`），即这两个 RJ12 是
> **同一对 UART 的两种接线形态**。本项目为单板方案，不使用扩展口，故不影响设计。

### 1.2.4 三个可选方案（按推荐度排序）

| 方案 | 做法 | 成本 | 能否得到"光照强度数值" | 推荐度 |
|---|---|---|---|---|
| **A. 用板载 AP3216C** | 什么都不用接，SDK 自带驱动 `base_07_i2c_ap3216c` | **¥0** | ✅ 可以（I2C 直接读 ALS 值） | ★★★★★ |
| B. 用模块的 `DO` | 接接口4 的 D0/D2/D4，自己写 PCF8574 读引脚 | ¥0 | ❌ 只能得到"亮/暗"二值 | ★★ |
| C. 外挂 I2C ADC | 在接口2 I2C 上挂 **ADS1115**（4 通道 16 位，约 ¥8） | ¥8 | ✅ 可读 4 路模拟量 | ★★★（本课题不需要） |

**推荐方案 A**，理由不只是"方便"，而是 AP3216C 客观上更好：

| | LM393 光敏模块 | 板载 AP3216C |
|---|---|---|
| 输出 | 模拟电压，需 ADC | **I2C 数字值，直接读** |
| 是否需要 ADC | **是（板子没有）** | 否 |
| 校准 | 需自己分压换算 | 出厂已校准 |
| 附加功能 | 无 | 接近 + 红外 |
| 驱动代码 | 需自己写 | **SDK 自带** |

> **答辩话术**：
> "光敏模块的模拟输出需要 ADC，而这块板子的 4 个扩展口暴露的是 I2C / SPI / UART / PCF8574 数字口，
> **没有引出任何 ADC 引脚**——这是我们从原理图上确认的。因此光照采集使用板载 AP3216C，
> 它本身就是数字光强传感器，精度和一致性都优于光敏电阻方案。
> 若日后要接模拟传感器，在 I2C 口挂一颗 ADS1115 即可，**架构上不需要改动任何代码**。"

> **兜底方案（不影响进度）**：先直接用 STM32 内部温度传感器（`ADC1_IN16`，无需任何外部元件）产出真实温度值——日志格式完全一致，等找到真实传感器再替换即可。

**传感器适配方案（三种情况都有解，不需要额外采购）**：

| 若温度传感器是 | 驱动方式 | 代码要点 |
|---|---|---|
| **DS18B20** | 单总线（1-Wire） | 需要 **4.7kΩ 上拉电阻**（VDD 与 DQ 之间）；时序对中断敏感，**必须关中断或用微秒级延时**，否则读数 `85.0`（复位默认值）——这本身就是一个绝佳的"真实异常"素材 |
| **DHT11** | 单总线自定义协议 | 需要 ≥1s 采样间隔、≥18ms 起始低电平；读失败率高（正常现象），**正好用来做 F1001 超时故障的真实触发源** |
| **NTC / LM75 / 无** | ADC 采样 或 I2C | NTC 需要查表/Steinhart-Hart 公式换算；**兜底方案**：用 STM32 内部温度传感器（`ADC1_IN16`，无需任何外部元件） |

> **兜底优先级**：真实传感器 > 内部温度传感器 > ADC 读电位器。**无论走哪条，日志格式完全一致**（见 `docs/02-log-spec.md` §2.4），所以不会影响其他组的工作。

### 1.3.1 ★ 关键决策：首版**不要**把 STM32 与 Hi3861 物理连线

这是本方案的一个刻意设计，不是省事：

```
方案（推荐）：两块板子各自通过 USB 连 PC，作为两个独立串口日志源
┌──────────────┐  USB(板载CH340)   ┌──────────────────────────┐
│ STM32F103C8T6│ ────── COM3 ─────▶│ PC：Python 双源采集与聚合 │
│ + 传感器      │                   │  collector(COM3, mcu)     │
└──────────────┘                   │  collector(COM5, hilog)   │
┌──────────────┐  USB(Type-C)      │                           │
│ FS-Hi3861    │ ────── COM5 ─────▶│                           │
└──────────────┘                   └──────────────────────────┘
```

| 理由 | 说明 |
|---|---|
| **并行开发** | W3~W5 期间两个组各调各的，一块板子出问题不阻塞另一块 |
| **零烧板风险** | Hi3861 是 3.3V 器件；不连线就完全不存在"STM32 输出 5V 打坏 Hi3861 RX"的风险 |
| **数据更真实** | 两个 COM 口 = 两条独立时间轴 + 两种日志格式 → **天然的多源异构日志素材**（本项目改为设备内跨模块关联，见 `docs/06` §8） |
| **演示更简单** | 插两根 USB 线即可，不会因为一根杜邦线接触不良翻车 |

**板间 UART 是 W4 之后的加分项**，等两边各自稳定再打通（引脚见 `docs/04-firmware.md` §0.1：**GPIO_5=RXD / GPIO_6=TXD / UART1**），届时只需两根线：`STM32_TX → Hi3861_RX` + **共地**，且 STM32 必须工作在 3.3V。

### 1.4.1 ★ 到底还要不要买传感器？（答辩会被问，先把答案定下来）

**结论：温度计不用买；DHT11 建议买（¥3–5）；光照传感器不用买。**

| 题目要求的 | 已有硬件 | 是否需采购 |
|---|---|---|
| 温湿度 | **板载 SHT20**（I2C 数字传感器，精度高于 DHT11） | ❌ 不需要 |
| 光照 | **板载 AP3216C**（真实 ALS 光强）+ 3 块光敏模块 | ❌ 不需要 |
| **DHT11** | 无 | ⚠️ **建议买** |

**买 DHT11 的两个理由（都不是"功能需要"）**：

**理由一：对得上题目字面要求。**
题目原文：「需单独再采购温湿度**DHT11**、光照传感器等环境感传感器」。评委手里拿着这段话。
用板载 SHT20 替代在技术上完全站得住，但**花 5 块钱就能让这句话变成"我们按要求采购了 DHT11 并完成驱动"，零争议。**

**理由二（更重要）：DHT11 是天然的故障源。**
DHT11 单总线时序敏感、**读失败率高**（这是它的公认特性）。
而题目要求「每 20-30 次上报后，随机触发一次"**传感器超时**"的 ERROR 日志」。
用 DHT11 时，这个超时是**真实发生的硬件故障**，而不是软件 `if (should_inject())` 编出来的。

| | 软件注入故障 | 真实 DHT11 故障 |
|---|---|---|
| 评委问"这故障是真的吗" | 需解释"我们模拟了…" | **"您看着，我把 DQ 线拔了"** |
| 根因分析的证据 | 构造的 | 硬件层面、可复现 |
| 报告可信度 | 中 | 高 |

> **一句话**：5 块钱换一个**现场能演示、评委能亲手验证**的真实故障源。这是建议买的核心理由。

**接线（买了之后）**：
```
DHT11 VCC  → 扩展口 3V3     ⚠️ 不要接 5V
DHT11 GND  → 扩展口 GND
DHT11 DATA → 任选一个空闲 GPIO（模块通常自带 4.7kΩ 上拉）
```
驱动要点：采样间隔 ≥1s、起始信号拉低 ≥18ms、上电需 1s 稳定期。
**读失败是正常现象**——正好作为 `F1001 传感器读取超时` 的真实触发源。

### 1.4.2 关于"只有一个传感器怎么做 6 个设备"

> **这是答辩必答题，答案要背熟。** 完整实现见 `agri_logger/parser/farm_model.py` 的模块注释。

#### 一句话回答

**6 个是【逻辑设备】，不是 6 个物理传感器。核心物理依据：6 个大棚共享同一片天空。**

#### 完整推理：为什么一个传感器就够

板载 SHT20 测的**不是"某个大棚的温度"，而是"整个园区的环境基准"**。
真实园区里 6 个大棚挨在一起，**同一天气、同一时段、同一片云**，温度本来就强相关
——不会一个 15℃ 一个 35℃。

差异来自**大棚本身的固定物理属性**：

| 大棚 | 物理差异 | 对数据的影响 |
|---|---|---|
| A 向阳主棚 | 南向、采光好 | 温度偏高、光照偏强、土壤偏干 |
| B 背阴棚 | 北侧被遮挡 | **温度偏低、湿度偏高、光照明显偏弱** |
| C 旧棚膜 | 透光差、保温差 | 居中 |
| D 新棚膜 | 透光好、升温快 | 白天偏高、散热也快 |
| E 近水渠 | 靠近水渠 | **湿度显著偏高** |
| F 大棚 | 面积最大 | 热惯性最大 → 变化最平缓 |

**模型公式**：

```
某个棚的数据 = 园区基准（真实测量）
             + 该棚的固定物理偏移（朝向/保温/土壤/遮挡）
             + 缓变惯性（一阶滞后跟随基准）
             + 微小传感器噪声（±0.1℃ / ±0.2%）
```

#### 这样比"买 6 个传感器"更严谨

| | 6 个独立传感器 | 1 个传感器 + 物理模型（本方案） |
|---|---|---|
| 数据相关性 | 同房间的 6 个传感器会高度相关，**仍需处理这种相关性** | **基准相同，相关性天然存在** |
| 成本 | ¥100+ | **¥0** |
| 接线维护 | 6 路 I2C，一个坏了查半天 | 无 |
| 可控性 | 无法控制"让 B 棚冷 2.7℃" | **可精确设定物理差异** |
| 可复现性 | 每次跑都不同 | **固定 seed 完全可复现** |
| 评测公平性 | 环境噪声不同，算法指标无法横向比较 | **输入完全相同，指标可比** |

> **反直觉但重要**：真买 6 个传感器放同一房间，读数几乎一样，
> **反而体现不出"多设备"的意义**。物理模型方案既真实又可控。

#### 可现场验证的证据

**真机实测日志**（6 个大棚差异都有物理依据）：

```

z=B  temp=25.9℃ humi=50.7% light=689   ← 背阴：最冷最湿最暗
```

A 比 B 高 2.7℃、B 的光照比 A 低 150 —— **对应"向阳 vs 背阴"，不是随机数**。

**自测脚本**（答辩现场跑，直接关闭"数据是不是编的"这个质疑）：

```powershell

```

三个硬指标：

- **稳态抖动**：温度 0.2℃、湿度 0.3% ← 噪声级别，不是逐轮乱跳
- **相关性**：6 棚变化方向一致率 **76~83%** ← 共享同一片天空；**随机数模型会接近 50%**
- **灌溉扰动**：湿度先陡升（62.7→71.8%）再缓降回 59.5% ← 符合物理直觉

#### 答辩话术（建议逐字背）

> "6 个是**逻辑设备**，不是 6 个物理传感器。关键物理依据是：**6 个大棚共享同一片天空**，
> 环境参数本来就强相关。所以板载 SHT20 测的是**园区基准**，6 个大棚在这个基准上叠加
> 各自的**固定物理属性**——朝向、保温性能、土壤湿度、棚体遮挡。我们的自测显示
> 6 个棚的变化方向一致率 76~83%，而随机数模型会接近 50%。
>
> **这样做比买 6 个传感器更严谨**：一是真放 6 个传感器在同一房间，读数几乎一样，
> 反而体现不出'多设备'；二是我们可以**精确控制物理差异**并**完全复现**，
> 便于公平评测异常识别算法。
>
> 报告里我们**明确标注了哪部分是真实采集、哪部分是物理模型派生**，不做模糊表述。"

### 2.1 方案 A（推荐）：双 COM 口 + 板载传感器

```
┌─────────────────────────┐         ┌──────────────────────────────┐
│  STM32F103C8T6          │         │  FS-Hi3861 开发板             │
│  · 温度传感器（待找）      │         │  · 板载 SHT20 温湿度传感器     │
│  · MH-Sensor 模块 ×1~3    │         │  · 板载 AP3216C（真实光强 ALS）│
│    VCC→3V3 GND→GND       │         │  · OLED / 蜂鸣器 / 风扇       │
│    AO→PA0(ADC1_IN0)      │         │  · 6 个 zone 任务并发          │
│  · USART1 打印日志        │         │  · 规范 hilog 输出到 USB-UART  │
│  · ST-Link → SWD 下载     │         │  · 板载 USB 转 UART 下载       │
└───────────┬─────────────┘         └──────────────┬───────────────┘
            │ USB（供电+串口，若无板载串口芯片          │ USB Type-C（板载 USB转UART）
            │      则用 USB-TTL 接 5V/GND/TX/RX）      │
            │ COM____                                 │ COM____
            ▼                                         ▼
      ┌──────────────────────────────────────────────────────┐
      │         PC：Python 工具同时读 2 个串口                │
      │  collector(COM_mcu,   kind="mcu")   ┐                 │
      │                                      ├→ 统一 LogRecord │
      │  collector(COM_hilog, kind="hilog") ┘   → 聚合与 LLM  │
      └──────────────────────────────────────────────────────┘
      ★ 两块板子之间【不需要】任何连线
```

**为什么推荐这个方案（答辩要能答）**：

| 优势 | 说明 |
|---|---|
| **开发解耦** | 两块板子独立调试，一块坏了不影响另一块。W3/W4 可以并行推进 |
| **不需要电平转换** | 两边都通过 USB 连 PC，物理上互不接触，没有 3.3V/5V 打架的风险 |
| **天然支持"多源日志"** | 两个串口 = 两个时间轴 = 两种格式 → 架构上只需增加一个 collector 源，`LogRecord` 不用改（本项目实际只用 Hi3861 单源） |
| **符合真实运维场景** | 真实工业现场就是"传感器节点 + 网关"各自上报，汇聚到平台侧做关联，而不是全部塞进一个 MCU |
| **答辩演示简单** | 插两根 USB 线即可，不会因为一根杜邦线接触不良翻车 |

**唯一的"缺点"**：两块板子之间没有物理连线，"STM32 采集 → Hi3861 转发"的链路没有跑通。这一点用**方案 B 补一次**即可（见下），但**它属于 W4 之后的加分项，不是前置条件**。

### 2.2 方案 B（加分项）：STM32 经 UART 接入 Hi3861

在方案 A 稳定运行后，**额外**打通板间链路，用于演示"边缘网关汇聚"：

```
STM32 USART2_TX (PA2) ────────▶ Hi3861 扩展口「接口3 UART」的 RX
STM32 USART2_RX (PA3) ◀──────── Hi3861 扩展口「接口3 UART」的 TX
STM32 GND           ─────────── Hi3861 GND          （必须共地！）
```

**接线前必做**：
1. **确认扩展 UART 口的引脚丝印/原理图**——FS-Hi3861 网盘资料里有原理图（`Hi3861鸿蒙开发板原理图.pdf`）。把 4 个扩展口的引脚定义抄到 §5 的记录表里；
2. **确认电平**：Hi3861 是 3.3V 器件，**TX 输出 3.3V** 送入 STM32 的 USART RX 是安全的（STM32 的 IO 多数为 5V 容忍，3.3V 判为高电平 OK）；但 **STM32 若在 5V 供电下 TX 输出 5V，会打坏 Hi3861 的 RX**。
   - **安全做法**：STM32 用 **3.3V** 供电（江科大板通常有 3.3V/5V 跳线帽），或串一个 **1kΩ 电阻 + 3.3V 稳压二极管**做分压/钳位；
   - **最简做法（强烈推荐）**：只用 **单线单向**——STM32 TX → Hi3861 RX，**不接反向线**，且 STM32 供 3.3V。只读不写，风险降到最低。
3. **共地**：两个独立 USB 供电的系统之间连信号线，**必须共地**，否则通信会出现随机乱码。

**这次联调的真正价值**：Hi3861 收到 STM32 的数据后，**用 `HiLogPrint()` 把它重新打印一遍**，格式为：

```
000512.334455 I A001 AgriSensor: z=A s=103 t=248 h=612 l=830 src=1 mseq=103
```

这样就实现了题目想要的"**Hi3861 采集真实环境数据**"——而且是通过 OpenHarmony 的规范日志格式输出的。这一行日志在答辩里非常有说服力。

### 2.3 方案 C（不推荐，仅记录）：STM32 作 I2C 从机

理论上可把 STM32 配成 I2C 从机接到扩展口的「接口2 I2C」上。**不推荐**，原因：
- STM32 硬件 I2C 从机模式配置复杂、时序容易死锁（业界公认坑）；
- I2C 是主从轮询，STM32 无法主动上报，日志实时性差；
- 收益（省一根线）远小于风险。

**了解这个方案的存在即可**，答辩时如被问"为什么不用 I2C"，用上面三条回答，反而是加分点。

## 3. 详细接线表

> **接线顺序很重要**：先接"验证工具链"的线，再接"采数据"的线，最后才考虑"板间通信"的线。
> **不要一次性把板间串口也接上**——出了问题你会分不清是哪一段的锅。

### 3.0 ★ 推荐的接线顺序（照着做，每步都可独立验收）

| 步骤 | 接什么 | 验收标志 | 风险 |
|---|---|---|---|
| **第 1 步** | FS-Hi3861 的 Type-C → PC | 串口助手（115200 8N1）能看到日志 | 无 |
| **第 2 步** | 三块传感器模块 → 面包板 3.3V/GND，万用表量 AO | 施加物理激励后 AO 电压变化（§1.2.1） | 低（**切记 3.3V**） |
| **第 3 步** | ST-Link → STM32 的 SWD（4 线，见 §3.1.1） | Keil 能看到芯片 ID，能下载点灯程序 | 低 |
| **第 4 步** | 传感器 → STM32（VCC/GND/AO/SIG） | 串口能看到 ADC 原始值与温度值 | 低 |
| **第 5 步** | STM32 micro-USB → PC（第二个 COM 口） | 设备管理器出现两个 COM 口 | 无 |
| **第 6 步（W4 再做）** | STM32 ↔ Hi3861 板间 UART | Hi3861 侧能打印 `src=1 mseq=` 的转发日志 | **中（有烧板风险）** |

### 3.1 方案 A 接线（推荐，"双 COM 口"）

#### 3.1.1 ST-Link ↔ STM32F103C8T6（SWD 下载/调试）

STM32 右侧 4 针排针即 SWD 接口。**丝印标注方向可能与你看到的相反，接线前先用万用表确认**：

| ST-Link | STM32 板 SWD 排针 | 说明 |
|---|---|---|
| `3.3V` | `3V3` | 若 STM32 已由 micro-USB 供电，**这针可以不接**（避免两路电源打架） |
| `SWDIO` | `DIO` / `SWDIO` | 数据线 |
| `SWCLK` | `CLK` / `SWCLK` | 时钟线 |
| `GND` | `GND` | **必须接**（共地是 SWD 能识别的第一前提） |

**接线前如何用万用表确认哪一针是 GND**（30 秒）：
1. 万用表打到**通断档**（蜂鸣档）；
2. 黑表笔按住板子上的 micro-USB 金属外壳（或任一大面积铜箔的 GND）；
3. 红表笔依次点 4 个针——**响的那一针就是 GND**；
4. GND 确定后，`3V3` 那一针在板上通常与一颗大电容/稳压芯片输出相连，可用电压档验证（约 3.3V）。

**验证是否连对**：Keil 里 `Options for Target → Debug → ST-Link Debugger → Settings`，能读到 `SW Device` 的 IDCODE 即成功。读不到就依次检查：共地、SWDIO/SWCLK 是否接反（这两根接反不会烧，放心对调）、ST-Link 驱动（`Tool/ST-Link/`）是否装好。

#### 3.1.2 模块与板子连 PC

| 从 | 到 | 线 | 说明 |
|---|---|---|---|
| STM32 micro-USB | PC USB 口 | USB 数据线 | 供电 + （若板载串口芯片）虚拟出 COM 口 |
| FS-Hi3861 Type-C | PC USB 口 | Type-C **数据线** | 板载 USB 转 UART，虚拟出 COM 口，用于下载 + 日志输出 |

> ⚠️ **先确认 STM32 有没有板载 USB 转串口芯片**：插上 micro-USB 后看设备管理器。
> - 出现 `USB-SERIAL CH340` 之类的 COM 口 → **有**，直接用，不需要额外买 USB-TTL；
> - 什么都没出现（只是通电了）→ 这块是最小系统板，USB 口只供电。此时需要把左上方的 `5V/GND/TX/RX` 4 针接到一个 USB-TTL 模块上才能看串口日志。

#### 3.1.3 传感器模块 → STM32

**第一块（已确认是光敏/光照模块，见 §1.2.1）**：

| 模块 | STM32 | 备注 |
|---|---|---|
| `VCC` | **3V3** | ⚠️ 绝不接 5V，见 §1.2.2 |
| `GND` | `GND` | 与 STM32 共地 |
| `AO` | `PA0`（ADC1_IN0） | 模拟量，主数据源 |
| `DO` | `PB0`（可选） | 不接也行；接了可做"数字量越限中断"演示 |

> **代码里的光强换算**：ADC 12 位（0–4095），参考电压 3.3V。
> `lux_rel = adc * 1000 / 4095` → 输出 0–1000 的"相对光照度"，日志里写 `l=830`。
> **注意**：光敏电阻的阻值-照度关系是非线性的（近似 `R ∝ 1/lux^γ`），我们**不追求物理精确**，只要求"单调可复现"。报告里要诚实写明"相对光照度，未做光度学标定"——这比假装精确更专业。

**第二、三块（识别结果出来后按类型接）**：

| 识别为 | 接法 |
|---|---|
| 光敏 / 火焰（模拟量类） | 同第一块：`AO` → `PA1`（ADC1_IN1），`DO` 可不接 |
| 湿度（模拟量类） | 同上，`AO` → `PA2`（ADC1_IN2） |
| 开关量类（DO 才有意义） | `DO` → 任意 GPIO（如 `PB1`），`AO` 可不接 |

> **一条纪律**：**一次只接一块新模块**。接上 → 串口看到正确读数 → 再接下块。三块一起接，出问题时分不清是哪块。

**温度传感器接 STM32（按型号）**：

| 型号 | 接线 |
|---|---|
| DS18B20 模块（3 针） | `VCC`→3V3，`GND`→GND，`DQ`→`PA1`（需 4.7kΩ 上拉到 3.3V，多数模块已板载） |
| DHT11 模块（3 针） | `VCC`→3V3，`GND`→GND，`DATA`→`PA1`（模块通常已带 4.7kΩ 上拉） |
| NTC 裸元件 | 与 10kΩ 电阻串联分压，中点→`PA1`(ADC)，供电 3.3V |
| **暂时找不到** | 用 **STM32 内部温度传感器**（`ADC1_IN16`），**无需任何接线**，先让链路跑通 |

## 4. 为什么"板载 USB 转 UART"这三点非常关键

FS-Hi3861 的**程序下载和日志输出都走 Type-C 的板载 USB 转 UART**，这带来三个好处，也是设计时的依据：

1. **日志与下载不冲突**：不需要像裸 Hi3861 模组那样纠结"UART0 既是控制台又是下载口"；
2. **扩展 UART 口可以自由用作数据通信**：这是方案 B 可行的硬件基础；
3. **PC 侧只看到一个 COM 口**：hilog 日志直接就是普通串口流，`pyserial` 开箱即用。

**但要确认一件事（W1 必做）**：这块板的 hilog 是否默认输出到 USB-UART？（有些教学板默认把 hilog 关掉以提升性能，只走裸机 `printf`。）
- **验证方法**：烧一个官方最小 demo，打开串口助手（115200 8N1），看是否有 `<时间> I A0xxx Tag: msg` 形式的输出；
- **若没有 hilog 服务**：直接用 `printf` 输出，并在固件里用宏补齐 hilog 前缀（见 `docs/02-log-spec.md` §2.3），**格式一致性不受影响**。

**串口参数（统一约定）**：

| 参数 | 值 | 说明 |
|---|---|---|
| 波特率 | **115200** | 10 秒约 115KB，足够 6 个 zone 的日志量 |
| 数据位/校验/停止位 | 8 / None / 1 | 8N1 |
| 流控 | None | — |
| 换行 | `\r\n` | 固件统一输出 CRLF，Python 侧 `rstrip("\r\n")` |

## 6. 常见问题排查（提前收藏）

### 6.0 ★★ 头号坑：DTR/RTS 电平决定 FS-Hi3861 能不能输出日志

**症状**：串口能正常打开、波特率试了 7 个、板子刚烧录成功，但**一个字节都收不到**。极易误判为"板子坏了"或"数据线不行"。

**实测四种组合（`python tools/uart_diagnose.py`）**：

| DTR | RTS | 实测结果 |
|---|---|---|
| **False** | **False** | ✅ **本项目采用** —— 两次实测均正常输出 |
| False | True | ❌ 0 字节 |
| True | False | ⚠️ 旧固件(base_06)下可用；换成我们的固件后 **0 字节** |
| True | True | ❌ 0 字节 |

**结论**：**不要在打开串口后主动驱动 DTR/RTS，保持都不设置（False）板子最稳定。** 因此 `tools/serial_capture.py` 的 `open_port()` 默认 `dtr=False, rts=False`。

> **为什么这个坑特别坑人**：网上大量教程推荐 `dtr=False` 是"防止开串口时板子重启"的防御性写法，另一些又推荐 `dtr=True`。**两种说法都能找到依据，但只有实测才知道哪种适用于你的板子。**
> 更麻烦的是：**同一块板子在不同固件下表现可能不同**（我们实测就遇到了）。所以一旦出现"0 字节"，**第一件事是跑 `uart_diagnose.py`，不要盲猜波特率、不要怀疑数据线**。

**另一个必知的时序现象**：串口打开后，板子可能需要**按一次复位键**才开始输出完整启动日志。实测按下复位键后立刻出现：

```
ready to OS start
sdk ver:Hi3861V100R001C00SPC025 2020-09-03 18:10:00
FileSystem mount ok.
wifi init success!
[agri_logger] stage-1 start: zone=A period=5000ms
I2C SHT20 Init is succeeded!!!
000000.054000 I A001 AgriSensor: 1 1 2 277 3 460 7 54 z=A
```

> **排查顺序固化下来**（遇到"收不到数据"就按这个走）：
> 1. `--list` 确认端口在不在 → 2. `--scan-baud` 排除波特率 → 3. `uart_diagnose.py` 遍历 DTR/RTS → 4. 确认没有被 Monitor / 串口助手占用 → 5. 按复位键。

### 6.1 其他常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| PC 认不到开发板 COM 口 | 用了"只充电"的 Type-C/USB 线 | 换一根确认能传数据的线 |
| 串口有输出但全是乱码 | 波特率不对 / 晶振不匹配 | 跑 `python tools/uart_diagnose.py`，或逐个试 115200 / 921600 / 9600 |
| **能打开串口但 0 字节** | **DTR/RTS 电平不对（见 §6.0）** | 跑 `uart_diagnose.py`；默认用 `dtr=False, rts=False` |
| **报 `PermissionError: 拒绝访问 COM3`** | **DevEco 的 Monitor 或串口助手正占用该端口** | 关掉它们（Windows 独占访问，同一 COM 口只能被一个程序打开） |
| **烧录卡在 `Connecting, please reset device...`** | Hi3861 串口烧录需要手动触发同步 | **按一下板子复位键**（正常流程，不是坏了） |
| **烧录成功但日志全是"未解析"** | 用的是官方 demo 的裸 `printf`，**没有 hilog 前缀** | 切到 `agri_logger:agri_logger`（见 `docs/04` §1.5）。这恰好说明日志规范的必要性 |
| **改了代码但现象没变** | 只点了 Stack Analysis（它只分析旧固件，不编译） | **必须点 `Rebuild`**，并确认固件时间戳更新。判断方法：`allinone.bin` 的时间，或反查里面有没有你的字符串 |
| 模块 AO 一直是 0 或一直是 3.3V | VCC 未接 / 敏感元件被完全遮住 / 电位器拧到底 | 万用表逐点量；先测 VCC 是否有电 |
| **模块接上后 ADC 读数恒为 4095** | 模块 VCC 接了 5V，AO 输出超过 ADC 量程 | **立即断电**，改接 3V3；量 AO 是否 ≤ 3.3V |

> **最后一条是新手最容易踩的坑**：调试时"DevEco Monitor 和 Python 抢串口"，两边都收不到数据，还以为是代码问题。**开发期用一个，验收期用 Python。**
