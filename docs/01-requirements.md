# 01 需求分析与选题定位

## 1. 这个题目到底在考什么

把题目原文拆开看，其实只有四件事，而且**权重是递增的**：

| 题目原文 | 真实考点 | 权重 | 常见失分点 |
|---|---|---|---|
| (1) Hi3861 场景模拟程序或真实数据采集 | **日志规范性**——你自己造的日志，字段能不能支撑后面的解析和聚合 | 20% | 日志全是自由文本，没有 seq、没有 zoneID，后面聚合无从下手 |
| (2) 串口/ADB 采集与解析 | **工程稳定性**——会不会断线、会不会丢日志、字段解析率 | 25% | 只演示"跑通一次"，一拔线就崩，没有重连和丢包统计 |
| (3) 异常模式识别 | **AI 用得对不对**——关键词库是基础，LLM 是增强，两者怎么配合 | 30% | 把整段日志无脑丢给 LLM，既贵又慢，还幻觉 |
| (4) 智能告警与报告 | **可读性与可信度**——报告能不能指导人干活，引用是否真实 | 25% | LLM 编造不存在的日志行、"疑似内存泄漏"但没有任何证据行号 |

**一句话抓住题目意图**：这不是"写个脚本调个 API"的作业，而是**"如何把非结构化日志变成可运维结论"的完整工程链路**。答辩时最能加分的不是"我调用了大模型"，而是"我知道什么时候**不该**调用大模型"。

## 2. 两条路线的取舍（题目自己给了两个选项）

题目 (1) 给了两条路：**"Hi3861 多任务模拟程序"**（复杂场景）或 **"真实传感器采集"**（简单场景，如温室大棚需另购 DHT11）。

你们的情况：**有 Hi3861、有 STM32、有温度传感器、没有湿度/光照传感器**。

### 我们的选择：**两者融合，主次分明**

```
主路线（占 70%）：Hi3861 多任务模拟程序 —— 满足题目"复杂工业场景模拟"的高分选项
                  ↓ 但模拟数据不能凭空编，要有物理锚点
真实锚点（占 30%）：真实传感器 —— 提供真实温度/湿度/光照值，作为派生数据的基准
```

**融合方式**（已按实拍硬件确定，见 `docs/03`）：
- **真实数据源有三处**：① Hi3861 板载 **SHT20**（真实温湿度）；② Hi3861 板载 **AP3216C**（真实光强 ALS）；③ STM32 + 外接 **MH-Sensor 模块**（真实光照/火焰/湿度，型号待实测识别）。
- Hi3861 固件用这些**真实值 ± 噪声**派生出 **6 个逻辑大棚（Zone-A~F）** 的完整日志流——同一园区的大棚环境参数强相关，所以派生的数据是"围绕真实环境值的合理分布"，而不是随机数。
- STM32 的日志作为**独立的第二数据源**通过第二个串口进入采集器，构成多源关联分析的基础。

**为什么这样最优**：
- 选了"复杂场景"路线 → 拿高分档；
- 有真实传感器锚点 → 满足题目对"真实环境数据"的要求，答辩时可以说"我们不是纯软件模拟"，而且**现场可以用手遮住传感器让告警真的响起来**；
- 现有硬件已覆盖题目提到的温湿度与光照采集 → **零额外成本**（DHT11 建议补买一个，仅约 ¥3–5，理由见 README §0.3，属答辩加分而非功能必需）。

## 4. 技术指标（写进技术报告的目标值）

| 指标 | 目标 | 说明 |
|---|---|---|
| 日志生成速率 | 6 Zone × (1 条上报/5s + 心跳) ≈ 1.5~3 条/秒 | 可调，演示时调快到 10 条/秒压测 |
| 解析成功率 | ≥ 99% | 含真机与模拟器两种源 |
| 字段完整率 | ≥ 99.5% | 必须有值的字段缺失率 |
| 异常召回率 | ≥ 85% | 对注入的 13 组故障场景（28 个故障码全覆盖） |
| 误报率 | ≤ 10% | 正常流量被判为异常的比例 |
| LLM 判定准确率 | ≥ 80% | 100 条人工标注样本 |
| 模板压缩率 | ≥ 60% | `1 - 模板数/原始不同文本数` |
| 告警去重率 | ≥ 70% | 同根因告警合并比例 |

> **指标不是喊口号**：每个指标都必须有 `eval/` 下的脚本能一键算出来，答辩时现场跑。没有脚本的指标不要写进报告——评委会问"你怎么算的"。

## 6. 与参考资料的关系（答辩时要能说出来）

| 参考资料 | 我们借鉴了什么 | 我们做了什么不同的事 |
|---|---|---|
| 华为 HiLog 日志打印文档 | 日志级别定义（DEBUG/INFO/WARN/ERROR/FATAL）、domainID 规则（`0x0~0xFFFF` 系统保留，应用用 `0x10000+`）、tag 长度限制 | 在 HiLog 标准字段之外扩展了 `zone`/`seq`/`faultcode` 三个自定义字段，用**标准字段追加**的方式，不破坏原格式可解析性 |
| FaultLoggerd 组件文档 | 故障类型体系（崩溃/卡死/内存/进程）、崩溃日志的"信号 + 栈 + 现场"三段结构 | 把 FaultLoggerd 的异常分类思想搬到**轻量设备日志**上，设计了我们自己的故障码字典 `Fxxx` |
| 华清远见《智慧农业》项目 | 场景（NFC 配网、MQTT、温湿度监测、阈值自动灌溉）、数据采集过程 | 该项目面向"功能实现"，我们面向"**日志可观测性与智能分析**"——同样的大棚，我们关心的是它产生的日志而非它的功能 |
| 以往毕业设计文档 | 章节结构、工作量分布 | 我们额外补充了**评测章节**（标注集、指标、消融实验），这是多数毕设缺失的部分 |

**答辩金句**（可背）："我们不是做了一个智慧农业系统，而是做了一个**能看懂智慧农业系统日志的运维大脑**。农业只是载体，可观测性才是本体。"

## 7. 项目边界（明确不做什么）

主动声明边界，是技术成熟度的表现：

- **不做**：真实的 OpenHarmony 内核态崩溃（需要 RK3568 级别的板子，Hi3861 轻量设备不具备 FaultLoggerd 完整能力）；
- **不做**：生产级分布式日志系统（不引入 Elasticsearch/Kafka，用 SQLite + JSONL 足够，理由要说清："本课题目标是算法验证，不是基础设施选型"）；
- **不做**：模型微调（成本与数据量都不支撑，用提示词工程 + 少样本示例达到目标指标，并说明"何时才值得微调"）；
- **做**：完整的单机端到端链路 + 可复现的评测 + 可讲清的架构权衡。
