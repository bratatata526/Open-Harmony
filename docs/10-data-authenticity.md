## 2.5 怎么区分"注入的故障"和"真实硬件故障"

演示时一定会被问到"这些 ERROR 是真的坏了吗"。有**一条硬判据**，看 `zone` 字段：

| 类型 | zone | 产生路径 | 例子 |
|---|---|---|---|
| **注入的故障** | `z=A`~`z=F`（带棚号） | `inject_fault()` 故意产生，用于验证分析链路 | `E A001 AgriSensor: 1 118 5 1001 6 1 9 5001 z=A` |
| **真实硬件故障** | **`z=-`** | `SHT20_ReadData()` 真的返回失败 | `E A001 AgriSensor: 1 .. 5 1001 .. z=-` |

固件里真实失败路径传的是 `'-'`（与具体棚无关），注入路径传 `p->zid`。
**看到 `z=` 后面是字母，就是注入的；是 `-`，就是真坏了。**

典型注入链（`SCEN_SENSOR`，分配给 A 棚）：

```
F1001 传感器读取超时 (cost=5001ms, code=1 reset_timeout)
   └→ F1004 读数超出合理范围 (temp=-127.0℃，物理不可能值)
        └→ 降级运行 (state=3 degraded)，同时仍上报真实环境值 31.7℃
```

`-127.0℃` 是**故意的** —— 真实传感器不可能读出这个值，用它当"数据已失效"的标记。
**环境数据本身不受影响**：紧跟着那行 `temp=31.7℃` 才是真实读数。

> ⚠️ 这三行**不是板子坏了**，是故障注入器在按设计工作。
> 答辩时照实说："这是我们主动注入的故障，用来验证分析链路能不能把
> 『超时 → 数据失效 → 降级』这条因果链识别出来。"

## 3. 模拟数据是怎么来的（为什么不能算"编造"）

模拟器不是"随机数生成器"，它实现了和设备端**同一套物理模型**：

```
园区基准  = 板载 SHT20 的真实读数（物理锚点）
          + 大棚个体差异（固定的物理偏移：朝向/保温/土壤/遮挡）
          + 缓变惯性（一阶滞后跟随基准）
          + 昼夜循环 + 灌溉扰动
          + 微小传感器噪声（±0.1℃ / ±0.2%）
```

模型实现在 `agri_logger/parser/farm_model.py`，固件里是 `ZONE_PROFILES` 数组。
**两边参数一一对应**（见 `docs/03` §1.4.2）。

**物理可验证性**（现场可跑）：

```powershell
.venv\Scripts\python.exe -m agri_logger.parser.farm_model
```

输出三个硬指标：

- **稳态抖动** 温度 0.2℃ / 湿度 0.3% ← 噪声级别，**不是逐轮乱跳**
- **相关性** 6 棚变化方向一致率 **76~83%** ← 共享同一片天空；**随机数模型会接近 50%**
- **灌溉扰动** 湿度先陡升（62.7→71.8%）再缓降回 59.5% ← 符合物理直觉

## 4. 关键证据：真机与模拟器**字节级同构**

**同一个解析器，对两者都是 100% 解析成功**：

```
真机 logs/multi.log
   总行 139  解析成功 139 (100.00%)  失败 0
   首条: level=I domain=A001 tag=AgriSensor zone=A seq=36 temp=28.4

模拟 eval/dataset/d2_v2.log
   总行 4475  解析成功 4475 (100.00%)  失败 0
   首条: level=I domain=A001 tag=AgriSensor zone=A seq=1 temp=22.4
```

**两者格式完全一致**，逐字段对照：

```
真机:  000014.011000 I A001 AgriSensor: 1 36 2 284 3 429 4 845 z=A
模拟:  000000.000000 I A001 AgriSensor: 1 1  2 224 3 576 4 782 z=A
       └─时间─┘    │ └4┘ └── 10 ──┘ └── 字段ID 值 成对 ──┘ z=设备
                级别  domain  tag
```

**并且真机数据里也能看到相同的物理差异**：

```
真机 multi.log:  z=A temp=28.4℃   z=B temp=25.7℃   z=C temp=28.0℃
                 ← A 向阳最热      ← B 背阴最冷
```

## 6. 答辩怎么讲（建议逐字背）

> **评委问**："这些日志是真实的还是你们编的？"

> **答**："分三层说清楚。
>
> **第一，设备端是真实的。** 我们在 Hi3861 上跑了 6 个逻辑大棚的多任务固件，板载 SHT20 采集真实温湿度——这是从板子串口抓下来的日志（展示 `logs/multi.log`），解析率 100%。现场可以遮住传感器或哈气，读数会变。
>
> **第二，系统链路是真实的。** 采集、解析、窗口聚合、LLM 分析、报告生成，整条链路都跑在真实数据上。
>
> **第三，看板演示用的数据集是模拟器生成的**，这一点我们明确标注。原因是它有 30 分钟、148 次故障注入和 ground-truth 标注，适合演示异常识别效果；真机跑 30 分钟再手动制造 148 次故障不现实。
>
> **但模拟不是编造。** 模拟器和固件实现的是**同一套物理模型**：园区基准来自真实 SHT20 读数，6 个大棚的差异来自朝向、保温、土壤这些**固定物理属性**。我们做了可验证性检查——6 个棚的变化方向一致率 76~83%，而随机数模型会接近 50%；稳态抖动只有 0.2℃，是传感器噪声级别而不是逐轮乱跳。
>
> **最关键的一点**：真机日志和模拟器日志**字节级同构**，同一个解析器对两者都是 100% 解析成功。所以模拟数据不是'另一套东西'，它是真机数据的可复现替代品——**这恰恰让算法评测变得公平，因为每次运行的输入完全相同。**"

## 8. 技术报告里怎么写

在"实验与评测"章节开头加一节 **§X.0 数据来源与真实性声明**：

```markdown
本研究的数据分两类：

（1）真机采集数据（logs/multi.log，139 行）：由 FS-Hi3861 开发板运行本项目的
    6 逻辑设备多任务固件产生，经板载 USB 转 UART 采集。用于验证采集与解析链路。

（2）带标注的模拟数据集（eval/dataset/d2_v2.log，4475 行，148 次故障注入）：
    由本项目开发的日志模拟器生成。模拟器与固件实现同一套多大棚环境模型
    （园区基准取真实读数，个体差异来自固定物理属性），两者输出字节级同构，
    同一解析器对两者的解析成功率均为 100%。

采用模拟数据集作为算法评测基准的原因：真实设备无法在 30 分钟内稳定复现
148 次故障；且模拟数据集保证了评测的**可复现性**——相同随机种子下
逐字节一致，使不同算法配置的指标可直接横向比较。

我们**明确区分**了真实采集与模型派生数据，未在任何环节将模拟数据
表述为真机数据。
```
