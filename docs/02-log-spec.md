## 1. 为什么必须先定规范

题目原文有一句关键提示：

> "注意模拟程序中日志生成的**规范性**，为后续聚合和分析打下基础。"

这句话是整道题的**题眼**。绝大多数组会栽在这里——设备端随手 `printf("temp=%d\n", t)`，到了 Python 端才发现：没有时间戳无法排序、没有级别无法过滤、没有模块标签无法分组、没有序号无法检测丢包、没有设备标识无法多设备聚合。

**一个真实对照**（我们实测过）：

```
官方 demo 的输出：  temperature = 28.13      humidity = 45.90
→ Python 解析器：0 个字段可提取，解析率 0%

我们的规范输出：    000120.456789 I A001 AgriSensor: 1 24 2 281 3 466 7 120456 z=A
→ Python 解析器：level/domain/tag/zone/seq/temp=28.1℃/humi=46.6%/tick 全部提取，解析率 100%
```

**同一份数据，只因为格式不同，可用性从 0 变成 100%。**

## 2. ⚠️ 三条硬约束（读了 SDK 源码后确认，直接决定格式设计）

在定规范之前，先在本地 SDK 里核实了三件事，**每一条都改变了设计**：

| 约束 | 来源 | 对格式的影响 |
|---|---|---|
| **`hilog_lite` 不支持 `%s`，最多 6 个数字变参，单条日志 ≤ 128 字节** | `src/base/hiviewdfx/hilog_lite/README_zh.md`：「**不支持 %s**」「单条日志最大长度 **128 字节**，超过将无法打印」 | **消息体禁止字符串值**（`detail=reset_timeout` 在真机上根本打不出来）→ 必须用**数字编码**。这直接催生了 §5 的故障码 + 错误码双层字典 |
| **`hilog_lite` 用「模块 ID」而非 domain 号**，需 `HiLogRegisterModule()`，最多 64 个 | 同上 | 轻量系统的 domain 字段是枚举，不是 `A001` 字符串。要在日志里打印 `A001` 得自己构造前缀 |
| **官方 FS-Hi3861 demo 全部用 `printf`，没有一个用 hilog** | 对 `vendor/hqyj/**` 全量 grep `HiLogPrint\|HILOG_` → **0 命中** | 该 SDK 下 hilog 组件虽启用但应用层未使用。**我们用宏构造同构前缀，既满足规范性又不侵入 SDK** |

> **这一节的写法就是本项目的方法论**：先读源码验证假设，再定规范。**不要写"应该可以"，要写"实测是"。**

## 3. 日志行格式

### 3.1 真机 / 模拟器输出

```ebnf
logline   = timestamp, SP, level, SP, domain, SP, tag, ": ", message, NL ;
timestamp = 6DIGIT, ".", 6DIGIT ;        (* 上电后秒.微秒，非绝对时间 *)
level     = "D" | "I" | "W" | "E" | "F" ;
domain    = 4HEXDIG ;                     (* A001~A007 *)
tag       = ALPHA, { ALPHANUM } ;         (* ≤31 字符 *)
message   = zone, SP, { fid, SP, value, SP } ;
zone      = "z=", ( "A".."F" | "-" ) ;
fid       = 1*2DIGIT ;                    (* 字段 ID，见 §4 *)
value     = [ "-" ], 1*7DIGIT ;           (* 纯整数，禁止字符串 *)
```

**实例（逐字段标注）**：

```
000120.456789 I A001 AgriSensor: 1 24 2 281 3 466 7 120456 z=A
└──── 时间 ────┘ │ └4┘ └── 10 ──┘ └────────── 消息体 ──────────┘
  上电后120.456789秒   domain       字段ID 值，成对出现，空格分隔
                级别   tag                             z= 设备号放最后
```

### 3.2 关键设计决策（答辩会被问）

| 决策 | 理由 | 代价 |
|---|---|---|
| **值必须是纯整数** | 硬约束：`hilog_lite` 不支持 `%s` | 可读性下降 → 用错误码字典还原（§5.4） |
| **小数用 ×10 存整数** | ① 绕开轻量平台浮点 printf 支持不确定的坑；② 模板挖掘时 281/282 都归一化为 `<*>`，不产生模板爆炸 | 解析时需 ÷10 |
| **字段 ID 而非位置参数** | 位置参数一多就没人记得住第 3 个是什么；ID 只有 1~2 位，成本极低，却让日志**顺序无关**、**人眼可读** | 每字段多 1~2 字节 |
| **字段用空格分隔** | 128 字节限制下每个分隔符都算钱；值必须是数字，天然不含空格 | — |
| **`z=` 放消息体最后** | 日志刷屏时，**最右一列是设备号**最好定位 | — |
| **时间戳用"上电后秒.微秒"** | Hi3861 **没有 RTC 电池**，上电后无绝对时间；编造假日期会导致排序错误 | 采集端需做时间轴换算（§6） |
| **不打印阈值 `thr`** | 阈值是**配置常量**，每条日志都带一遍纯属浪费空间 | 服务端从配置读取 |
| **用宏构造 hilog 前缀，不用原生 `HiLogPrint`** | 原生接口不支持 `%s`、需改 SDK 公共头文件注册模块（升级会被覆盖）；printf 输出的字节流与规范**完全同构**，解析器不需区分 | 需自己保证格式正确 → 用自动校验兜底（§9） |

### 3.3 单行长度预算（**必须遵守**）

```
999999.999999 W A006 AgriHealth: 1 99999 8 999999 15 999999 9 9999999 z=-
└── 15 ──┘└4┘└5┘└── 12 ──┘└──────────── 约 42 字节 ────────────┘
                                              总计 = 75 字节 ✅

最坏情况实测（极端值 + 最长 tag）：
  正常上报 6 字段   76 字节   余量 52
  健康检查 4 字段   75 字节   余量 53
  故障注入 4 字段   67 字节   余量 61
  通信类   4 字段   64 字节   余量 64
```

| 部分 | 典型 | 上限 |
|---|---|---|
| 时间戳前缀 | 15 | 15 |
| 级别 + domain + tag + `: ` | 22 | 40 |
| **消息体** | 30~50 | **70** |
| `\r\n` | 2 | 2 |
| **合计** | 60~76 | **≤ 128（硬上限）** |

> ⚠️ **超长的后果极严重**：`hilog_lite` 对超长日志是**静默丢弃**的——不报错、不截断、什么都不打印。
> 现象是"故障明明发生了，日志里找不到那一行"，你会怀疑串口丢数据，排查方向完全错。
> **对策**：采集端必须统计行长分布，`max > 128` 立即告警。我们的实现见 `docs/05`。

### 3.4 为什么用 `printf` 而不是原生 `HiLogPrint`（主动权衡）

本 SDK 的 `config.json` 里 `hilog_lite` 组件**默认已启用**。要用原生接口需三步：
① 改 `hiview_log.h` 的 `HiLogModuleType` 枚举加模块；② `HiLogRegisterModule()` 注册；③ `HILOG_INFO()` 打印。

**我们评估后选择不用**，理由：
1. 要改 SDK **公共头文件**，升级 SDK 时会被覆盖；
2. 不支持 `%s`、无 domain 字符串，输出格式与我们的规范不一致，反而要额外适配；
3. 应用层用宏构造同构前缀，**保持了与 OpenHarmony 日志规范的一致性，同时避免侵入 SDK**。

> **这是一条主动权衡，不是"不会用 hilog"。** 答辩时要这样讲。

## 4. 字段字典

### 4.1 前缀字段（必须有）

| 字段 | 类型 | 示例 | 说明 | 缺失后果 |
|---|---|---|---|---|
| `timestamp` | `秒.微秒` | `000123.456789` | 设备上电后时间 | 无法排序、无法算间隔 |
| `level` | enum | `I` | `D`/`I`/`W`/`E`/`F` | 无法过滤 |
| `domain` | 4 hex | `A001` | 业务域，见 §4.2 | 无法按子系统归类 |
| `tag` | str ≤31 | `AgriSensor` | 模块标签 | 无法按模块分组 |
| `z=` | char | `A`~`F` / `-` | 逻辑设备号；`-` 表示全局 | 无法多设备聚合 |

### 4.2 Domain 分配表（冻结，实现时不许串用）

| domain | 用途 | 代码归属 | 对应 SDK 模块 |
|---|---|---|---|
| `A001` | 环境传感（温湿度/光照采集） | `sensor_hub` | `base_06_i2c_sht20`、`base_07_i2c_ap3216c` |
| `A002` | 数据上报（MQTT/串口上行） | `report` | `network_05_wifi_mqtt` |
| `A003` | 设备自检与健康（内存/栈/心跳） | `health` | 需自行实现（`hi_mem_get_sys_info`） |
| `A004` | 执行器控制（灌溉/通风/蜂鸣器） | `ctrl` | `base_02_i2c_pcf8574_fan` |
| `A005` | 任务调度与并发（超时/队列） | 跨任务 | `kernel_01~08_*` |
| `A006` | 配网与通信（WiFi/MQTT 重连/NFC） | `net` | `network_01~06_*` |
| `A007` | 故障注入器（仅测试构建） | `fault_inject` | 需自行实现 |

> **domain 也是"跨模块因果关联"的基础**（`docs/06` §8 的因果规则表按 domain 匹配）。
> 一个 domain 对应一个代码模块 → 看到 domain 就知道去哪个文件排查，这正是运维需要的信息。

### 4.3 消息体字段表（**唯一真源**）

> **实现位置**：`agri_logger/parser/fields.py` 的 `FIELDS` 表。
> 固件（`log_def.h` 的 `agri_field_t`）、模拟器、解析器三方都从这里派生。

| ID | 名称 | 换算 | 单位 | 值域 | 说明 |
|---|---|---|---|---|---|
| `1` | `seq` | 原值 | — | 0~2³² | **单调递增序号**，丢包检测唯一依据 |
| `2` | `temp` | **÷10** | ℃ | -200~850 | 温度 |
| `3` | `humi` | **÷10** | % | 150~900 | 湿度 |
| `4` | `light` | 原值 | — | 0~1200 | 相对光照度 |
| `5` | `fault` | 查表 | — | 见 §5.2 | 故障码数值 |
| `6` | `code` | 查表 | — | 见 §5.4 | 错误码 |
| `7` | `tick` | 原值 | ms | — | 系统 tick |
| `8` | `heap` | 原值 | B | — | **剩余堆内存**（真实值，来自 `free_lmp`） |
| `9` | `cost` | 原值 | ms | — | 耗时 |
| `10` | `retry` | 原值 | — | — | 重试次数 / 连续失败次数 |
| `11` | `state` | 查表 | — | 0~3 | **状态机**：0=idle 1=irrigating 2=venting 3=degraded |
| `12` | `thresh` | ÷10 | — | — | 阈值（仅需强调时携带） |
| `13` | `rssi` | 取负 | dBm | — | WiFi 强度，**存正值**：`13 83` → -83dBm |
| `14` | `queue` | 原值 | — | — | 消息队列长度 |
| `15` | `miss` | 原值 | — | — | 漏喂次数 / 累计失败次数 |
| `16` | `zone_id` | 原值 | — | 0~5 | 设备编号 0=A…5=F（非首字段场景用） |

**三条硬约束**：

1. 值必须是**纯整数**（可带负号）；**不得出现字符串**
2. 值中不得出现**空格**（会破坏 `ID 值` 配对）
3. **单行总长 ≤ 128 字节**（含 `\r\n`）

## 5. 故障码与错误码字典

### 5.1 编码规则

```
F c s s
│ │ └── 序号 00~99
│ └──── 类别：1=感知层 2=通信层 3=系统层 4=业务/执行层 5=生命周期
└────── 固定前缀 F
```

### 5.2 故障码表（21 条，冻结）

| 故障码 | 数值 | 级别 | domain | 名称 | 判据（下游用） | 是否正常事件 |
|---|---|---|---|---|---|---|
| F1001 | 1001 | E | A001 | 传感器读取超时 | `cost > 1000` | 否 |
| F1002 | 1002 | E | A001 | 单总线复位无应答 | `fault=1002` | 否 |
| F1003 | 1003 | E | A001 | 数据校验失败 | `fault=1003` | 否 |
| F1004 | 1004 | W | A001 | 读数超出合理范围 | `temp < -200 或 > 850` | 否 |
| F1005 | 1005 | W | A001 | 数值越阈值 | 必带 `thresh` | 否 |
| F1006 | 1006 | E | A001 | 传感器离线 | 必带 `miss` | 否 |
| F2001 | 2001 | E | A006 | MQTT 连接失败 | 必带 `rssi` | 否 |
| F2002 | 2002 | E | A002 | 上报超时 | `cost > 3000` | 否 |
| F2003 | 2003 | W | A006 | WiFi 信号弱 | `rssi < 80`（→-80dBm） | 否 |
| F2004 | 2004 | W | A006 | 断线重连 | 必带 `retry` | **✅ 是** |
| F2005 | 2005 | E | A006 | 数据帧校验错 | `fault=2005` | 否 |
| F3001 | 3001 | E | A003 | 内存分配失败 | 必带 `heap` | 否 |
| F3002 | 3002 | E | A003 | 任务栈溢出 | 栈水位 > 90% | 否 |
| F3003 | 3003 | E | A005 | 任务调度超时 | `cost > 5000` | 否 |
| F3004 | 3004 | W | A005 | 队列积压 | `queue >= 8` | 否 |
| F3005 | 3005 | E | A003 | 看门狗即将触发 | `miss >= 2` | 否 |
| F3006 | 3006 | W | A003 | 空闲堆不足 | `heap < 4096` | 否 |
| F4001 | 4001 | W | A004 | 执行器超时 | `cost > 5000` | 否 |

### 5.3 六个 zone 的故障分工（保证日志多样性）

| zone | 主攻故障域 | 涉及故障码 |
|---|---|---|
| **A** | 传感器读取失败 | 1001, 1002, 1004, 1005 |
| **B** | 任务调度与并发 | 3003, 3004 |
| **C** | 内存（渐进式因果链） | 3006 → 3001 → 2002 |
| **D** | 看门狗 | 3005 |
| **E** | 执行器 | 4001, 4002 |

> 这是"智能聚合"的核心演示素材，见 `docs/06` §8。

## 6. Python 解析后的数据结构

### 6.1 `LogRecord`（全项目统一）

```python
@dataclass
class LogRecord:
    # ---- 定位 ----
    line_no: int
    evidence_id: str          # "hl:00001234" —— 报告引用用，可回查
    source: str               # hilog | mcu
    src_name: str             # "COM3" / "sim"

    # ---- 时间（双时间轴）----
    ts_device: float | None   # 设备上电后秒数
    ts_host: float            # 主机绝对时间
    ts_source: str            # device | host

    # ---- 前缀 ----
    level: str                # I
    domain: str               # A001
    tag: str                  # AgriSensor
    message: str              # 原始消息体
    raw_line: str             # 原始整行（永不丢弃，可重放）

    # ---- 语义字段 ----
    zone: str | None          # 'A'
    seq: int | None           # 24
    fault: int | None         # 1002
    fault_tag: str | None     # 'F1002'
    fault_name: str | None    # '单总线复位无应答'
    code: int | None          # 1
    detail: str | None        # 'reset_timeout'（由 code 查表得来）
    is_normal_event: bool     # True = 正常运维事件，不算异常
    values: dict[int, int]    # 原始字段 ID → 原始值
    physical: dict[str, str]  # 字段名 → 带单位可读值，如 {'temp': '28.1℃'}

    # ---- 便捷属性 ----
    @property
    def temp(self) -> float | None   # 已 ÷10
    @property
    def humi(self) -> float | None   # 已 ÷10
    @property
    def is_error(self) -> bool       # level in (E, F)
    def summary(self) -> str         # 一行摘要
```

### 6.2 时间轴换算（Hi3861 无 RTC，必须处理）

设备输出的是"上电后秒数"。采集端需映射到主机绝对时间：

```python
class TimeBase:
    """滑动窗口中位数估计时钟偏移，抗串口抖动"""
    def observe(self, ts_device, ts_host):
        self.offsets.append(ts_host - ts_device)
    def to_host(self, ts_device):
        return ts_device + statistics.median(self.offsets)   # 中位数抗离群
```

**设备重启检测**（不处理会导致时间轴错乱）：

```python
if last_ts_device >= 0 and ts_device < last_ts_device - 5.0:
    boot_id += 1; timebase = TimeBase()      # 判定为重启
```
判据：**`ts_device` 大幅回退** + **`seq` 归零**，双重确认。

### 6.3 落盘结构

- **JSONL**：每行一个 `LogRecord`，可 grep、可重放
- **SQLite**：`logs` / `templates` / `windows` / `reports` / `alerts` 五张表
- **原始行永不丢弃**：`raw_line` 必须保留，便于用新规则重放历史数据（**可重放性是加分点**）

```python
    r"^\[STM32\]\s+(?P<ts>\d+)\s+(?P<level>[DIWEF])\s+"
    r"(?P<tag>[A-Za-z][A-Za-z0-9_]{0,30}):\s*(?P<msg>.*)$"
)

# 消息体：zone
RE_ZONE = re.compile(r"(?:^|\s)z=(?P<zone>[A-Za-z0-9_-])")
```

**解析器的三条纪律**（已在 `parser.py` 实现 + 单测覆盖）：

1. **永不抛异常**——脏数据返回 `None` 并计数，绝不让一行乱码打断采集循环
2. **永不丢原始行**——`raw_line` 原样保留
3. **行长必须监控**——`>128` 字节在真机上会被**静默丢弃**

## 9. 三方一致性自动校验（防止"改一处忘一处"）

**这是本规范能落地执行的关键机制。** 三方共享同一张字段表，靠代码验证而非人工比对：

```
════════ 三方一致性校验 ════════
模拟器输出 84 行 → 解析器成功 84 行，失败 0 行
✅ 模拟器 / 固件字段表 / 解析器 三方一致
```

**运行方式**：

```powershell
.venv\Scripts\python.exe -m agri_logger.parser.parser            # 契约自测
.venv\Scripts\python.exe tools/openharmony_log_sim.py --selftest # 三方校验
```

**校验原理**：模拟器吐出的**每一行**都喂给真正的解析器解析，有一行不通就报错退出。
固件侧则通过 `log_def.h` 的枚举与 `fields.py` 的表逐项对应（见 §10 变更流程）。

> **为什么需要它**：我们踩过这个坑——采集器曾自带一套正则，设备端换格式后它还在找旧的
> `zone=`/`seq=`，打印出 `z=A z=A s=None` 的错乱结果。**根因是解析逻辑有两份实现。**
> 现在从结构上消除了这种可能，详见 `docs/09-troubleshooting-log.md` 坑 8。
