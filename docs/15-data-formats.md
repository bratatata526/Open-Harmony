## 0. 先对齐口径（写错这一句，后面全错）

* **物理上只有一块 FS-Hi3861 开发板 = 一个传感器节点**：板载 SHT20 出温度 / 湿度，板载 AP3216C 出光照（ALS）。
* 固件把这**同一组真实读数**在软件里**派生**成 6 个**逻辑设备** `Zone-A ~ Zone-F`，
  代表园区 6 个大棚**共享同一片天空**。**不是 6 个传感器，也没有外接模块、没有第二路数据源。**
* 每 5 秒一轮，6 个 zone 交错输出（实测一轮约 5.02 秒，见 `log_def.h` 注释）。
* `z=-` 表示**整机级**日志（健康检查 / 启动 / 模式上报），不属于任何一个 zone。
* UI 文案请写「6 个逻辑设备」或「6 个大棚」，**不要写「6 个传感器」**。

## 第 1 层：设备 → 串口 的物理传输格式

### 1.1 物理参数（照抄即可）

| 项目 | 值 | 出处 |
|---|---|---|
| 波特率 | **115200**（命令行默认值，可用 `--baud` 改） | `tools/serial_capture.py` `--baud default=115200` |
| 数据位 / 校验 / 停止位 | **8N1**（`EIGHTBITS` / `PARITY_NONE` / `STOPBITS_ONE`） | `tools/serial_capture.py` `open_port()` |
| 帧边界 | **一行一帧**，设备以 `\r\n` 结尾 | `log_def.h` `agri_log_emit()` 末尾写 `'\r' '\n'` |
| 编码 | ASCII（消息体只有数字与空格）；采集端按 UTF-8 容错解码 | `serial_capture.py` `decode("utf-8", errors="replace")` |
| 单行硬上限 | **128 字节**（含行尾） | `parser.py` / `serial_capture.py` 的 `MAX_LINE_BYTES = 128` |
| 流控 / 帧头 / 长度字段 / 校验和 | **全部没有** | 见 1.5 |
| 复位方式 | 串口 **DTR + RTS 同时拉高**才释放复位（板载 CH340 自动复位电路） | `serial_capture.py` `open_port()` 注释（实测四种组合） |

**采集端怎么切帧（真实实现，逐行可对）**：

```python
# tools/serial_capture.py（节选，逻辑与源码一致）
chunk = ser.read(4096)            # 一次 read 很可能只拿到半行
buf += chunk
while b"\n" in buf:               # ★ 只按 \n 切帧
    raw_bytes, buf = buf.split(b"\n", 1)
    raw = raw_bytes.decode("utf-8", errors="replace").rstrip("\r")   # 去掉 \r
    nbytes = len(raw_bytes) + 1   # 近似线上字节数（含 \n）
```

> 所以 `\r\n` 与裸 `\n` **都能工作**，但 `\r` 必须剥掉 —— 否则 `z=A` 后面会带一个 `\r`，
> 正则里 `(?P<msg>.*)$` 会把它吃进消息体，`RE_ZONE` 仍能匹配（`\s` 之后），
> 但 `raw_line` 会多出不可见字符，前端"复制原文"时会出现奇怪的换行。

### 1.2 字节级可视化（真实最长行，70 字节）

取自 `eval/dataset/d2_v2.log` 第 1000 行的真实内容（全 4475 行里最长的一行，**70 字节**）：

```text
001000.000000 I A001 AgriSensor: 1 213 2 225 3 618 4 779 7 1000000 z=A
└─────┬─────┘ │ └─┬┘ └────┬────┘ │ └─┬─┘ └─┬─┘ └─┬─┘ └─┬─┘ └───┬───┘ └┬┘
   13 字节    1   4    10 字节   1   5     5     5     5      9      3 字节
  上电后秒.微秒 │  domain  tag    空格  seq  temp  humi  light  tick   z=A
               │
             级别（1 字节）
```

| 段 | 内容 | 本行字节数 | 上限 / 约束 |
|---|---|---|---|
| 时间戳 | `001000.000000` | 13 | 固定 "6 位秒.6 位微秒"（秒可更长，正则 `\d{6,}`） |
| 空格 + 级别 | ` I` | 2 | 级别只能是 `D I W E F` 之一，1 字节 |
| 空格 + domain | ` A001` | 5 | 4~5 位十六进制（`[0-9A-Fa-f]{4,5}`） |
| 空格 + tag + `:` + 空格 | ` AgriSensor: ` | 13 | tag `≤31` 字符，正则 `[A-Za-z][A-Za-z0-9_]{0,30}` |
| 消息体 | `1 213 2 225 3 618 4 779 7 1000000` | 33 | 每个字段 "ID 值" 后跟一个空格 |
| 空格 + zone | ` z=A` | 4 | `z=` + 一个字符（`A`~`F` 或 `-`） |
| 行尾 | `\r\n` | 2 | 不计入上面 70，计在 128 的预算里 |
| **合计** | | **70（+2）** | **≤ 128** |

**实测字节分布（`eval/dataset/d2_v2.log`，4475 行）**：最短 45、最长 70、平均 57.6 字节。
**余量充裕 —— 但余量不是"可以随便加字段"的理由，见下一条。**

### 1.3 ⚠️ 坑 1：超过 128 字节会被**静默丢弃**（不是截断、不报错）

```c
/* log_def.h：为什么必须自己数长度 */
#define AGRI_MSG_MAX   120   /* 超过这个值 hilog_lite 会静默丢弃 */
```

```python
# parser.py：采集端唯一的"发现手段"
MAX_LINE_BYTES = 128
nbytes = len(raw.encode("utf-8", errors="replace")) + 2   # 按 \r\n 估算线上字节数
if nbytes > MAX_LINE_BYTES:
    self.over_limit += 1        # 只计数，不阻断 —— 这行在真机上"根本没出现过"
```

**后果（这是本文最需要前端记住的一条）**：

* 板上**什么都没打印**，不是"打了一半"。所以日志里**那一行不存在**，
  既搜不到、也画不出、也不会进证据段。
* 现象是"故障明明发生了，日志里却没有那一行"，很容易被误判成"串口丢数据 / 采集脚本 bug"，
  排查方向完全错。
* 超长只在**采集端计数**（`meta.longest_line` / `meta.over_limit`，见 `docs/14` §3.1）。
  **前端必须把这两个数显示出来**（顶部"数据健康"徽标）：它 > 0 就意味着"你现在看到的日志流是残缺的"。
* 注意：解析器**不会**因为它超长就拒收（本例 131 字节的行照样解析成功）。
  "解析成功"与"真机发得出来"是两件事。

### 1.4 ⚠️ 坑 2：没有帧头、没有长度、没有校验

一帧的全部身份信息就是**行首的 `6+ 位数字.6 位微秒`**。正则 `RE_HILOG` 就靠这个认行：

```python
RE_HILOG = re.compile(
    r"^(?P<ts>\d{6,}\.\d{6})\s+"
    r"(?P<level>[DIWEF])\s+"
    r"(?P<domain>[0-9A-Fa-f]{4,5})\s+"
    r"(?P<tag>[A-Za-z][A-Za-z0-9_]{0,30}):\s*"
    r"(?P<msg>.*)$"
)
```

**后果**：

* 串口噪声、波特率抖动、固件里插一句不带时间戳的 `printf`，都会让**整行解析失败**，
  不存在"部分字段可用"这种中间态。坏行计数在 `parser.report()` 里，并且**按原因分类**
  （`空行` / `非日志格式（噪声/乱码）` / `有 hilog 时间戳但前缀不完整` / `像 MCU 日志但格式不符` / `其他`），
  比一个"成功率 97%"的数字有用得多。
* 前端不要尝试"从流里猜帧"。**帧 = 一行**，这就是全部规则。

### 1.5 ⚠️ 坑 3：上电瞬间必然有几行"非规范"日志（属正常现象）

固件的开机横幅是**直接 `printf` 的常量文本**，刻意不带 hilog 前缀（因为要打版本号、
tick 频率这些"字符串信息"，而 `hilog_lite` 不支持 `%s`）：

```c
/* agri_logger_multi.c 开机横幅（节选，源码原样拼接） */
printf("[agri_logger] FW=v2.8 mode=");
/* SINGLE_DEVICE_MODE 为真时：*/ printf("single-device(真实传感器直通), period=5000ms, tickfreq=");
/* 否则：                     */ printf("6-zones(逻辑设备), period=5000ms, tickfreq=");
printf("%sHz, heap=", tb);        /* tickfreq=100Hz → 1 tick = 10ms */
printf("%s\r\n", hb);
```

同一处还有 `[agri_logger] stage-2 init: 6 zones`、`[agri_logger] task created, stack=8192 bytes`、
`[agri_logger] FATAL: create task failed`。

把它们喂给真实解析器，结果是（已实测）：

```text
输入: [agri_logger] FW=v2.8 mode=6-zones(逻辑设备), period=5000ms, tickfreq=100Hz, heap=14436
输出: None                       ← 解析失败
失败原因分类: "其他"（因为它以 '[' 开头，既不匹配 hilog 前缀，也不是 MCU 格式）
```

**后果 / 前端该怎么做**：

* 启动瞬间出现 **2~4 行解析失败是正常的**，不要据此弹"固件异常"。
* 判断标准用**比例**而不是"有没有"：解析失败率持续 > 1%，才提示"日志格式不符，
  可能板上不是当前固件"。
* 开机横幅里的 `FW=v2.8` 是**版本判据**：现象没变时先看这一行，能立刻区分
  "改了代码没烧录"和"真的没修好"。
* 另外：这些行**不进** `LogRecord`、不进窗口、不进报告证据段。前端"原始日志"页面
  若只显示解析成功的行，那就永远看不到横幅 —— 这是设计上的取舍，不是 bug。

### 1.6 ⚠️ 坑 4：解析"成功"不等于数据正确（旧固件的活证据）

`logs/multi.log` 是**旧固件**（用 `snprintf` 拼字段）采的，里面有两种真实损坏。
它们都能被解析器"成功"解析：

```text
# logs/multi.log 第 13 行（注意 "15" 和 "9" 之间是两个空格：值缺失了）
000014.016000 I A003 AgriHealth: 1 2 8 1 15  9 6 z=-
→ 解析结果: values = {1: 2, 8: 1, 15: 9}   ← 字段错位！"9" 被当成了 miss 的值
   physical = {'seq': '2', 'heap': '1B', 'miss': '9'}

# logs/multi.log 第 27 行（负号被截断：-1270 打成了 "-"）
000015.047000 W A001 AgriSensor: 1 3 5 1 6 3 2 - z=A
→ 解析结果: values = {1: 3, 5: 1, 6: 3}   ← fault=1 / code=3，temp 直接丢成 None
```

**后果**：

* 这种"坏行"不报错、不计数，会安静地把**错误数字**送进图表。
  `temp=None` 会被某些作图库当 0 画出来（`0℃` 的假曲线，见第 4 层 §4.4）。
* **规避方法**：只采信**当前固件（`FW=v2.8`）**采的日志；`logs/multi.log` 这类历史文件
  只能用来看结构，`heap` / `miss` / 负数相关字段**不可信**（`docs/09` 已记录此事）。

### 1.7 前端注意事项（第 1 层小结）

1. **不要自己切字节流**。后端已经把行切好、解析好，前端只拿 JSON。
2. `meta.longest_line` / `meta.over_limit` 要显示：它们说明"日志流是否完整"。
3. 解析失败率按**比例**判断，启动瞬间天然失败几行。
4. 原始行里可能有不可见字符（`\r`、ANSI 转义已被剥掉）；"复制原文"直接用后端给的 `raw`。

## 第 2 层：日志行（hilog 同构）格式

### 2.1 四段结构

```ebnf
logline   = timestamp, SP, level, SP, domain, SP, tag, ": ", message, SP, zone ;
timestamp = 6DIGIT, ".", 6DIGIT ;        (* 上电后秒.微秒，不是绝对时间 *)
level     = "D" | "I" | "W" | "E" | "F" ;
domain    = 4HEXDIG ;                    (* A001~A008 *)
tag       = ALPHA, { ALPHANUM | "_" } ;  (* ≤ 31 字符 *)
message   = { fid, SP, value, SP } ;     (* "ID 值" 成对，顺序无关 *)
zone      = "z=", ( "A".."F" | "-" ) ;   (* 放消息体最后 *)
```

真实行（`eval/dataset/d2_v2.log#L1953`，报告里被引用为 `hl:00001953`）：

```text
000780.000000 E A003 AgriHealth: 1 157 5 3005 6 14 15 2 z=D
└─────┬────┘ │ └─┬─┘ └───┬────┘  │ │   │  │ │  │ │  │ │ └┬┘
   780.0 秒   │  A003  AgriHealth │ │   │  │ │  │ │  │ │  z=D → 逻辑设备 D
  （设备上电  │  设备自检        │ │   │  │ │  │ │  │ └── miss=2（看门狗漏喂 2 次）
   后的相对  E=ERROR             │ │   │  │ │  │ │  └──── code=14 → wdt_feed_missed
   时间）                        │ │   │  │ │  │ └─────── fault=3005 → F3005 看门狗即将触发
                                  │ │   │  │ └───────── seq=157（该 zone 内单调递增）
                                  │ │   └─────────── 字段 ID 1 的值 = 157
                                  │ └─────────────── 消息体开始（"ID 值" 逐对出现）
                                  └───────────────── tag 与消息体之间的 ": "
```

### 2.2 级别 `D/I/W/E/F`：语义、排序、配色

| 级别 | 语义 | 排序值 | 该不该让用户看见 | 真机/数据集实际量 |
|---|---|---|---|---|
| `D` | DEBUG 调试 | 0 | 默认折叠 | **0 条**（本项目不打 D 级） |
| `I` | INFO 正常业务（周期上报、健康检查） | 1 | 是（可折叠） | 4327 条 |
| `W` | WARN 需关注但不影响功能 | 2 | 是，黄色 | 66 条 |
| `E` | ERROR 功能受损 | 3 | 是，红色 | 82 条 |
| `F` | FATAL 致命（系统级） | 4 | 是，红底/最高优先级 | **0 条**（保留未用） |

排序值定义在 `parser.py`（`--min-level` 过滤、"ERROR 及以上"判断都靠它）：

```python
LEVEL_ORDER: dict[str, int] = {"D": 0, "I": 1, "W": 2, "E": 3, "F": 4}
```

**终端配色（本项目现有实现，可直接照搬成前端调色板）**：

```python
# tools/serial_capture.py
return {"D": "\033[90m", "I": "\033[0m", "W": "\033[33m",
        "E": "\033[31m", "F": "\033[41m"}.get(level, "\033[0m")
```

> ⚠️ **坑**：`F` 级在现有真机日志与评测数据集里**一次都没出现**。
> 但解析器、接口、报告都支持它。**前端必须支持 5 级**，
> 只按 4 级写 `switch` 会在遇到 `F` 时掉进 default 分支（表现为"级别空白/无色"）。
> **后果**：真机上如果真的 FATAL 了，恰恰是最需要醒目的那一条，结果它是唯一没颜色的。

### 2.3 domain：模块号（8 个）

消息体的 `domain` 决定"出了事去哪个模块查"。8 个值冻结，不许串用：

| domain | 用途 | 典型故障码 | 本数据集行数 |
|---|---|---|---|
| `A001` | 环境传感（温湿度 / 光照） | F1001~F1006 | 2107 |
| `A002` | 数据上报（MQTT / 串口上行） | F2002 | 2086 |
| `A003` | 设备自检（堆 / 栈 / 心跳 / 生命周期） | F3001 F3002 F3005 F3006 F5001~F5004 | 220 |
| `A004` | 执行器控制（灌溉 / 通风 / 蜂鸣器） | F4001 F4002 | 13 |
| `A005` | 任务调度（超时 / 队列 / CPU） | F3003 F3004 F3011 | 27 |
| `A006` | 配网与通信（WiFi / MQTT 重连） | F2001 F2003 F2004 F2005 | 22 |
| `A007` | 故障注入器（**仅测试构建**） | （不产生业务故障） | 0 |
| `A008` | 系统异常（看门狗 / 死机 / 非法内存） | F3007~F3010 | 0（现有日志未出现） |

> ⚠️ **坑**：`A007` / `A008` 在现有数据集里是 **0 行**，但在**自测场景**里会出现
> （例：`logs/alerts.jsonl` 采信的自测证据 `... E A008 AgriCrash: ... 5 3009 ...`）。
> 前端做 domain 筛选下拉框时，**不要用"当前数据里出现过的 domain"动态生成**，
> 否则现场演示切到系统崩溃场景时，`A008` 的筛选项会凭空消失。
> **后果**：现场演示最想讲的那个维度（死机 / 看门狗）恰好点不出来。

### 2.4 tag：模块标签（真实取值共 10 个）

| tag | 来源 | 说明 |
|---|---|---|
| `AgriSensor` | 固件 + 模拟器 | 传感采集（`A001`） |
| `AgriReport` | 固件 + 模拟器 | 数据上报（`A002`） |
| `AgriHealth` | 固件 + 模拟器 | 健康检查 / 生命周期（`A003`） |
| `AgriTask` | 固件 + 模拟器 | 任务调度（`A005`） |
| `AgriCtrl` | 固件 + 模拟器 | 执行器（`A004`） |
| `AgriComm` | 固件 + 模拟器 | 通信（`A006`） |
| `AgriSelfCheck` | 固件（开机一行） | **数值转换自检行**，专测 0 / 4 位 / 5 位 / 负数 |
| `AgriMode` | 固件（周期重发） | 设备模式上报（注入开/关），`A003`，`z=-` |
| `AgriCrash` | 模拟器（system_crash 场景） | 系统崩溃（`A008`） |
| `AgriFault` | 模拟器（故障注入） | 故障注入器（`A007`） |

自检行真实期望内容（`docs/09` 记录了真机实测 `FW=v2.1`，当前源码为 `v2.8`）：

```text
I A003 AgriSelfCheck: 1 0 5 1001 8 20480 15 -355 z=-
                      ↑零 ↑4 位  ↑5 位    ↑负数（故意超域，专测符号分支）
```

> ⚠️ **坑**：`AgriSelfCheck` 行里 `fault=1001` 是**假故障码**（用来测 4 位数打印），
> 它会让"故障码统计"里凭空多一个 F1001。**前端做"本窗口故障码"列表时要能过滤这个 tag**，
> 否则用户会看到一个从未真实发生的"传感器读取超时"。
> **后果**：开机瞬间的统计数字被一行自检污染，且难以解释。

### 2.5 zone：`z=A`~`F` 与 `z=-`

| 取值 | 含义 | 真机/数据集情况 |
|---|---|---|
| `z=A` … `z=F` | **逻辑设备**（6 个大棚）。物理上仍是同一块板、同一组读数 | d2_v2.log 里每个 zone 约 706~729 行 |
| `z=-` | **整机级**：不属于任何单个 zone（健康检查、启动、设备模式） | d2_v2.log 里 179 行 |

`z=-` 的真实行（`eval/dataset/d2_v2.log#L37`，注意 seq 恒为 0）：

```text
000010.000000 I A003 AgriHealth: 1 0 8 20447 z=-
                              ↑ seq=0（整机级日志不参与 zone 内序号递增）
```

> ⚠️ **坑（真实踩到）**：`-` 会**混进设备列表**。报告元信息表的"涉及设备"直接用了
> `sorted(window.zones)`，而 `zones` 里包含 `-`：
>
> ```text
> | 涉及设备 | -、A、B、C、D、E、F |        ← reports/W0014_任务卡死与资源耗尽.md 真实内容
> ```
>
> 而告警里的 `device` 字段是**过滤过的**（`summary._device_label()` 丢掉 `-`）：
> `"device": "全部 6 个设备"`。**同一个窗口，报告与告警的设备描述不一致。**
> **后果**：如果前端自己从报告表格里正则抠"涉及设备"来做筛选，会拿到 7 个值（含 `-`），
> 和告警卡片的"全部 6 个设备"对不上。**统一用 `/api/alerts` 的 `device`，或自己过滤 `-`。**

### 2.6 消息体：`<字段ID> <值>` 成对出现、顺序无关

三个设计理由（都来自真实平台约束，不是风格偏好）：

| 约束 | 事实 | 导致的设计 |
|---|---|---|
| `hilog_lite` **不支持 `%s`** | SDK `hilog_lite/README_zh.md` 明写 | 消息体里**禁止字符串值** → 只能放数字，可读性靠"码表还原" |
| 单条日志 **≤ 128 字节** | 同上 | 分隔符只能是 1 个空格；`z=` 放最后（刷屏时最右列最好定位） |
| 最多 6 个数字变参 / 平台 printf 不可靠 | `log_def.h` 踩坑记录 | 字段数量受限，且**整型转换自己写**（`agri_u2a`），不用 `snprintf` |

**为什么用"数字 ID"而不是固定位置**：

* 纯位置参数（只有值）→ 字段一多就没人记得住"第 3 个是什么"，可读性归零。
* ID 只有 1~2 位数字，成本极低，却换来 **人眼可读** + **顺序无关**：
  **加字段不会破坏老解析器**（老解析器只认自己知道的 ID）。

实测验证"加字段不破坏老解析器"（真实解析器行为）：

```text
输入: 000030.000000 I A001 AgriSensor: 1 9 2 281 21 5 z=A
       （21 是尚未定义的字段 ID）
输出: values = {1: 9, 2: 281}      ← 未知 ID 21 被安静忽略，其余照常解析
```

字段顺序确实无关，同一组数据这样写也解析成一样：

```text
A: 000000.000000 I A001 AgriSensor: 1 1 2 224 3 576 4 782 7 0 z=A
B: 000000.000000 I A001 AgriSensor: 2 224 4 782 7 0 3 576 1 1 z=A
   → 两条解析出的 values 完全相同（{1:1, 2:224, 3:576, 4:782, 7:0}）
```

> ⚠️ **坑**：配对规则是"数字 ID 后面紧跟一个**整数**，否则跳过 1 个 token"。
> 所以**值缺失或值非数字会让后续字段整体错位**（§1.6 的 `15  9` 就是活例子）。
> **后果**：图表上的 `miss=9` 看着完全合理，没人会发现它其实是 heap 字段的值。
> 这是"解析成功但数据错"的典型，只能靠"只用当前固件采的日志"来规避。

### 2.7 前端注意事项（第 2 层小结）

1. **不要解析日志行**。`/api/logs`、`/api/live/logs` 已经给结构化字段；`raw` 只用于"查看原文"。
2. 级别 5 个都要支持（含 `D`、`F`）；排序值 `D<I<W<E<F`。
3. domain 下拉框写死 8 个，别按数据动态生成。
4. `z=-` 是合法值，不要当 `null` 处理；但做"设备"维度时**必须过滤掉 `-`**。
5. `AgriSelfCheck` 是自检行，统计故障时要排除。

| 值 | 含义 |
|---|---|
| 0 | 指令地址非对齐 |
| 1 | 取指访问错 |
| 2 | 非法指令 |
| 4 | Load 地址非对齐 |
| 5 | Load 访问错 |
| 6 | Store 地址非对齐 |
| 7 | Store/AMO 访问错 |

### 3.4 字段 18 `addr`：出错地址 / `mtval`

* 含义：非法地址访问、踩内存时**硬件记录的地址**（`mtval`）。单位在字段表里记为 `B`（字节偏移）。
* 展示：代码统一用 `0x%X` 输出且按 32 位掩码（`int(addr) & 0xFFFFFFFF`）。
  `4096` → `0x1000`。**前端展示也用十六进制**，十进制会让人以为是"第 4096 个字节的序号"。
* 只在"死机 / 非法访问"类日志里出现（F3009 / F3010 / F3002 等），
  且**日志里没有函数名、没有任务名** —— 别在 UI 上写"崩在 xxx 函数"。

### 3.5 字段 11 `state`：状态机编码

| 值 | 语义 | 出处 |
|---|---|---|
| 0 | `idle` | `fields.py` `STATE_NAMES` |
| 1 | `irrigating`（灌溉中） | 同上 |
| 2 | `venting`（通风中） | 同上 |
| 3 | `degraded`（降级运行） | 同上 |

真实行（`eval/dataset/d2_v2.log#L549`）：

```text
000220.000000 W A001 AgriSensor: 1 47 11 3 2 248 3 610 z=A
→ state=3（degraded）  temp=24.8℃  humi=61.0%
```

> ⚠️ **坑（代码与文档不一致，已核实）**：`STATE_NAMES` 虽然定义了，
> 但**没有被 `format_physical()` 使用** —— 所以 `physical["state"]` 的值是字符串 `"3"`，
> 不是 `"degraded"`。`docs/02` §4.3 与 `docs/14` §2.3 都写了"查表"，
> 与当前代码行为**不符**。
> **后果**：前端若直接把 `physical.state` 显示给用户，界面上会出现一个裸数字 `3`；
> 若按文档以为会拿到 `"degraded"` 而没做映射，就会渲染空白。
> **做法**：自己维护 `0→idle / 1→irrigating / 2→venting / 3→degraded` 的映射，
> 用 `values["11"]`（原始数值）判断，不要依赖 `physical`。

### 3.6 已定义但现有日志"从未出现"的字段

`12 thresh`、`16 zone_id`、`17 mcause`、`18 addr`、`19 cpu`、`20 memfail`。

| 字段 | 什么时候才会出现 |
|---|---|
| `12 thresh` | 仅在"要强调阈值"的越限日志里（`docs/02` 说默认不打印，省字节） |
| `16 zone_id` | 仅当 zone 不在首字段位置、需要数字编号时 |
| `17` / `18` | 系统崩溃 / 非法内存访问类场景（模拟器 `--scenario system_crash`） |
| `19 cpu` | CPU 过载场景（F3011） |
| `20 memfail` | 内存池申请失败统计（F3001 场景） |

> ⚠️ **坑**：图表/详情页若把这些字段当"必有列"渲染，会**整列空白**；
> 若用 `values["19"]` 直接下标取值，Python 端是 `KeyError`、JS 端是 `undefined → NaN`。
> **后果**：曲线出现 NaN 断点或整页报错。正确姿势是 `values[x] ?? null`。

### 3.7 前端注意事项（第 3 层小结）

1. **缩放**：`temp`、`humi`（以及极少见的 `thresh`）是 **×10 的整数**，要 ÷10。
   接口返回的已经是物理值（`/api/zones` 等），**只有看原始 `raw` 行时才需要自己除**。
2. `rssi` 存正值（`111` = -111dBm），展示要取负。
3. `state` 自己映射（别指望 `physical` 给中文/英文名）。
4. 字段可能**缺失**，一律按"未知"处理，不要补 0。
5. `addr` 用十六进制显示。

## 第 4 层：解析后的结构化记录（`LogRecord`）

### 4.1 字段表

解析器内部用 `evidence_id` / `ts_device` / `raw_line` 这些名字；
**接口层把它们改成了 `eid` / `ts` / `raw`**（`docs/14` §2.1）。两套名字都要认识：

| 解析器字段 | 接口字段 | 类型 | 含义 |

| `evidence_id` | `eid` | string | 证据编号 `hl:00001953`（`hl`=hilog，`mcu`=MCU 扩展位）。**报告引用它，可按它回查原始行** |

### 4.3 `physical` 是**给人看的字符串**（带单位），不要解析它

真实取值形态（全部来自上面两条真实记录 + 同数据集）：

| 键 | 值（字符串） | 说明 |
|---|---|---|
| `temp` | `"22.4℃"` / `"-127.0℃"` | 已 ÷10，带 `℃` |
| `humi` | `"57.6%"` | 已 ÷10，带 `%` |
| `light` | `"782"` | 无单位 |
| `fault` | `"3005"` | 原始数值（**不是** `F3005`） |
| `code` | `"14"` | 原始数值（**不是** `wdt_feed_missed`） |
| `miss` | `"2"` | 无单位 |
| `heap` | `"3072B"` | 带 `B` |
| `cost` | `"6000ms"` | 带 `ms` |
| `rssi` | `"111dBm"` | 带 `dBm`，**且是正值** |

> **后果**：任何 `parseFloat("22.4℃")` 都会在某一天变成 `NaN`，
> 或者更糟 —— `parseInt` 得到 `22` 看着"差不多对"，于是没人发现精度丢了。
> **规则**：`physical` 只用于**文本展示**；画图请用 `/api/zones`、`/api/timeline` 的数值字段
> （它们已经是 `float`，见 `docs/14` §3.3、§3.4）。
> 若真的必须从 `LogRecord` 取数，用 `values["2"] / 10`，别碰 `physical`。

### 4.4 `null` 的语义：**未知 / 不存在**，画图要断点，绝不能补 0

| 字段 | 何时为 `null` | 正确渲染 | 错误渲染的后果 |
|---|---|---|---|
| `ts` | 极少数无法取到设备时间的行（`_to_float` 失败） | 用相邻点或标"时间未知" | 排序错乱 |
| `zone` | 行里没有 `z=` | 归入"未标注" | — |
| `fault` / `fault_name` | 普通日志（绝大多数） | 不显示故障徽标 | 显示 "null" 或空徽标 |
| `detail` | 没有 `code` 字段 | 不显示错误短语 | 显示 "-"（看着像数据缺失） |
| `physical.temp` | 该行没带字段 2（如健康检查行） | **曲线断点**（不入点） | **图上出现 0℃** |

真实例子：`logs/multi.log#L27`（旧固件负数截断）解析后 `temp = null`：

```python
values = {1: 3, 5: 1, 6: 3}     # 没有字段 2
physical = {..., }               # 没有 temp
# 前端若写 `Number(rec.physical.temp ?? 0)` → 0
```

> ⚠️ **坑（最关键的一条）**：`null → 0` 让曲线"贴地"，看起来像"大棚温度 0℃，传感器坏了"，
> 实际上是"这一行根本没有温度"。运维会据此得出**完全错误**的结论。
> **规则**：`null` = 该点不存在。ECharts 用 `null` 入数组自动断线；
> Recharts/Chart.js 需要 `connectNulls: false` / `spanGaps: false`。

### 4.5 双时间轴：为什么有 `ts_device` 还有 `ts_host`

* Hi3861 **没有 RTC 电池**，上电后没有绝对时间 → 日志里只能是"上电后秒.微秒"。
* `ts_device` 是**设备自己算的**（`osKernelGetTickCount()/osKernelGetTickFreq()`，本平台 100Hz，1 tick = 10ms）。
* `ts_host` 是**PC 收到这一行时的本地时间**，用来回答"这条日志是今天几点出现的"。

> ⚠️ **坑（真实踩过，`log_def.h` 有完整记录）**：曾把 tick 当 1ms 写死，
> 时间戳慢了 **约 10 倍**（真实过 40.1 秒 → 设备只前进 4.1 秒）。
> **后果**：分析端按"设备秒"切 60 秒窗口，实际切成了约 600 秒，窗口语义全错；
> 日志静默检测也永远不触发（间隔被显示成 0.5 秒）。
> **前端该做什么**：图表 X 轴统一用 `ts`（设备相对秒），**不要拿 `ts` 当绝对时间显示成日期**；
> 需要"几点几分"时，用告警的 `created_at` 或报告的 `生成时间`（本地时间字符串）。

### 4.7 为什么"正常运维事件"必须排除在异常计数之外

`fields.py` 里三个故障码被显式标记为 `is_normal=True`（正常业务事件）：

| 故障码 | 名称 | 为什么算正常 | 真实行 |
|---|---|---|---|
| `F2004` | 断线重连 | WiFi 抖动后自动恢复，是**功能正常**的表现 | `000290.000000 W A006 AgriComm: 1 61 5 2004 6 9 10 2 z=F` |
| `F4002` | 灌溉状态变更 | 灌溉开关是**业务动作**，不是故障 | （本数据集未出现；`A004`） |
| `F5001` | 设备启动 | 每次上电都有一条，正常生命周期事件 | （本数据集未出现；`A003`） |

排除逻辑（打分与聚合都走它）：

```python
# fields.py
def is_normal_event(code: int) -> bool:
    """★ 这是误报率的关键：F2004 断线重连、F4002 灌溉状态变更、F5001 设备启动
      都是【正常运维事件】，必须排除在异常之外。不做这一步，误报率会显著偏高。"""
    fd = FAULTS.get(code)
    return fd.is_normal if fd else False
```

```python
# windows.py score_window()：故障码那一路的分母只算"异常"的
for tag, cnt in w.fault_count.items():
    code = int(tag[1:])
    if not F.is_normal_event(code):
        abnormal += cnt
p = min(1.0, abnormal / 2.0)
```

**真实影响（已实测统计）**：`eval/dataset/d2_v2.log` 里 `F2004` 出现 **4 次**
（`#L735` / `#L1310` / `#L2852` / `#L4090`，间隔 230 秒，是规律性的重连巡检）。
若不排除：

* 这 4 条 `W` 级日志会进"ERROR/WARN 计数"，窗口 `W` 数虚高；
* **故障码那一路**（权重 0.25）会把它们当异常 → 本来 `abnormal=0` 的窗口
  `min(1, 4/2)=1.0`，直接白送 **0.25 分**，跨过异常阈值（0.25）→ **健康窗口被误报成异常**。
* 聚合指纹也会从 `FEAT-WARN` 变成 `FW-2004` → **同一个族被劈成两类**，报告数量翻倍。

> ⚠️ **坑**：前端如果自己算"异常 KPI"，**必须用 `/api/faults[].normal` 或自己的码表排除**
> （`docs/14` §2.5 已强调）。后端打分已排除，前端不排除就会**和后端数字对不上**，
> 这种"两个数字都显示在屏幕上、互相矛盾"的问题最难解释。
> **后果**：现场演示时"异常窗口"数量前后不一致，一眼就是 bug。

### 4.8 前端注意事项（第 4 层小结）

1. 记住三套名字的映射：`evidence_id↔eid`、`ts_device↔ts`、`raw_line↔raw`。
2. `physical` 只做文本；数值请走接口的数值字段，或 `values["ID"] / scale`。
3. `values` 的键是**字符串**。
4. `null` 是断点，不是 0。
5. 时间轴用 `ts`（相对秒），别当绝对时间。
6. 异常计数排除 `F2004` / `F4002` / `F5001`。

> 说明那份报告由**更早一版数据集**生成。**后果**：前端如果按指纹做 key 或做"同类合并"，
> 跨版本对比会全部错配。指纹只适合**展示**，聚合请用 `/api/families`。
>
> ⚠️ **坑 B（标题里的下划线）**：文件名形如 `W0014_任务卡死与资源耗尽.md`
> （`<window_id>_<标题>.md`），Markdown 里若把文件名原样写进正文，
> `_` 会被当成斜体语法。**渲染前请对文件名做转义或放进代码块。**

### 5.3 「二、证据」—— 程序从原始日志取，不经过模型

这一段是**防幻觉的核心机制**，也是全报告唯一"事实 100% 可靠"的部分：

```python
# analyzer/rca.py — 证据段由程序生成
def render_evidence_block(self, records, window=None) -> str:
    if not records:
        return "（无有效证据）"
    return "\n".join(f"[{r.evidence_id}] {r.raw_line}" for r in records)
```

* 每行固定形如 `[hl:00001953] 000780.000000 E A003 AgriHealth: 1 157 5 3005 6 14 15 2 z=D`。
* `hl:00001953` 的**数字就是原始日志行号**（本例对应 `eval/dataset/d2_v2.log` 第 1953 行，
  已逐行核对）。`hl` 后面的 8 位是 `%08d` 补零，所以按字符串排序仍然等于按行号排序。
* LLM 只输出"证据编号"，程序拿编号去 `EvidenceValidator` 里查；**查不到的编号直接不渲染**
  （编造的编号无法进入报告）。
* 代码块**没有语言标注**（` ``` ` 后为空），因为内容是设备原始文本。
  渲染时请用 `text`/`plaintext` 高亮，别用 `log`（会乱上色）。

**真实降级报告里的证据段（可以对照）**：`reports/W0014_看门狗即将触发.md` 有 10 条，
`W0014_任务卡死与资源耗尽.md` 有 6 条 —— 条数取决于 `window.evidence(max_lines)` 挑了多少
（优先级：故障行 > ERROR > WARN）。**所以不同报告的证据条数不一样，不要写死。**

> ⚠️ **坑**：证据行的内容是**原始日志行**，里面 `z=D`、`2 -1270` 这些对普通用户是天书。
> **后果**：直接把证据段当正文渲染，用户看不懂。建议：默认折叠成"证据（6 条）"，
> 展开后用等宽字体 + 逐行高亮 `[eid]` 部分；`eid` 做成可点击（跳到 `/api/logs` 里那一条）。

### 5.4 三种"分析引擎"取值 + 降级横幅（**必须显示**）

`to_markdown()` 里的引擎标注与横幅：

```python
badge = {"llm": "LLM 语义分析", "rule": "本地规则引擎（降级）",
         "raw": "仅原始事实（降级）"}.get(self.mode, self.mode)

banner = ""
if self.mode == "rule":
    banner = ("\n> ⚠️ **本报告由本地规则引擎生成**（LLM 不可用）。"
              "根因结论基于故障码字典，未做跨模块语义推理。\n")
elif self.mode == "raw":
    banner = ("\n> ⚠️ **本报告仅包含原始事实与统计**（LLM 与规则库均不可用），"
              "不含根因推断，请人工分析。\n")
```

| `mode` | 表格里"分析引擎"显示 | 额外横幅 | 当前是否会产生 |
|---|---|---|---|
| `llm` | `LLM 语义分析（模型 deepseek-flash）` | 无 | ✅ 有 LLM Key 时 |
| `rule` | `本地规则引擎（降级）` | `> ⚠️ **本报告由本地规则引擎生成**（LLM 不可用）…` | ✅ LLM 不可用时 |
| `raw` | `仅原始事实（降级）` | `> ⚠️ **本报告仅包含原始事实与统计**…` | ❌ **代码里预留，当前版本不会产生** |

真实降级报告对照（`reports/W0014_看门狗即将触发.md`，注意第 18~20 行的引擎行 + 横幅）：

```markdown
| 置信度 | 65% |
| 分析引擎 | 本地规则引擎（降级） |

> ⚠️ **本报告由本地规则引擎生成**（LLM 不可用）。根因结论基于故障码字典，未做跨模块语义推理。
```

**前端必须做的事（关系可信度与答辩诚实性）**：

1. **引擎标注不可隐藏、不可省略**。`LLM 语义分析` 与 `本地规则引擎（降级）` 的区别
   是"做了跨模块语义推理"还是"只按故障码字典查表"。
2. 有 `> ⚠️` 横幅时，**渲染成醒目的提示条**（黄色/琥珀色），不要当普通引用块。
3. 报告列表页也建议带引擎徽标（从 `/api/reports` 拿不到就得读 markdown 里的"分析引擎"行）。
4. 降级报告的"三、疑似根因"通常是**固定套话**（例：
   「跨模块因果链：内存类故障 → 上报超时 → 传感器读取异常 → 任务调度异常。存在先后依赖关系，建议按链首模块排查。」），
   处置建议也是固定三档。**不要把它渲染得像 LLM 的深度推理结果。**

> ⚠️ **坑**：`raw` 这个值在 `to_markdown()` 的 badge/banner 里**有分支**，
> 但全代码库没有任何地方把 `Report.mode` 设成 `"raw"`
> （`tools/dashboard_server.py` 与 `tools/analyze_demo.py` 都写 `"llm" if ... else "rule"`）。
> **后果**：前端若为 `仅原始事实（降级）` 专门做一套 UI，当前永远是死代码；
> 但**仍需容忍这个值**，因为它是契约里预留的第三种引擎。

### 5.5 另一类报告：健康报告（结构不同，要能识别）

`reports/健康报告_样例.md`（未发现异常时的报告）**不是 5 段式**，结构是：

```markdown
# 系统健康报告 —— 未发现异常

| 项目 | 值 |          ← 元信息表 11 行（含"记录数""时间跨度""窗口数""异常窗口""级别分布"）
## 一、结论
## 二、故障码统计
## 三、这个结论意味着什么
## 四、如何验证监测系统确实在工作
---
<sub>…本报告不调用 LLM：没有异常就没有根因可推…</sub>
```

| 区别 | 根因报告 | 健康报告 |
|---|---|---|
| 文件名 | `<window_id>_<标题>.md`（如 `W0014_看门狗即将触发.md`） | `健康报告_MMDD_HHMMSS.md` |
| 摘要引用块 | 有 `> **摘要**｜…` | **没有** |
| 章节数 | 5 个（一~五） | 4 个（一~四，标题不同） |
| 证据代码块 | 有 | **没有** |
| 引擎标注 | 有"分析引擎"行 | 没有（落款里说明不调用 LLM） |

> ⚠️ **坑**：若前端用"必须存在 `> **摘要**｜` 行"来判断"是报告"，
> 健康报告会被判成"格式错误"。
> **后果**：演示到"系统健康"那一刻反而报错。
> **做法**：按文件名前缀 `健康报告_` 或"是否存在 `## 二、证据`"来区分两类模板。

### 5.6 报告文件与接口的关系

| 项目 | 值 | 出处 |
|---|---|---|
| 写入目录 | `reports_live/`（运行时自动生成，**不入库**）、`reports_llm/`（预留，暂空）、`reports/`（**入库的样例报告**） | `dashboard_server.py` `REPORT_DIRS` |
| 根因报告文件名 | `"%s_%s.md" % (window_id, 标题)` | `dashboard_server.py` |

| 接口 | `/api/reports` 列表、`/api/report?name=` 取原文 | 字段见 `docs/14` §3.13 / §3.14 |

### 5.7 渲染清单（Markdown 特性白名单）

报告里**实际用到**的 Markdown 语法只有这 7 种，渲染器按这个范围配就够：

| 语法 | 出现在哪 | 注意 |
|---|---|---|
| `#` 一级标题 | 第 1 行 | 全报告唯一 H1；列表页标题就取它 |
| `>` 引用块 | 摘要行 + 降级横幅 | 摘要行**带加粗**与全角 `｜` |
| `**加粗**` | 表格值、摘要素 | — |
| `` `行内代码` `` | 窗口编号、聚合指纹 | 用于等宽显示 ID 类值 |
| 表格 | 元信息表（12 行）、健康报告表格 | 2 列；分隔行是三段短横线、**不带对齐冒号** |
| 代码块（无语言） | 证据段 | 用 `text` 高亮 |
| `---` + `<sub>…</sub>` | 落款 | **`<sub>` 是 HTML 标签**：若 sanitize 白名单不含 `sub`，落款会整段消失 |

> ⚠️ **坑**：`<sub>` 若被 sanitize 掉，**落款里的"数据来源 / 证据引用条数"就没了** ——
> 这两项是"可回查"的承诺，答辩时正要用。
> **后果**：报告看起来像"没有出处"的 AI 输出。渲染器请放行 `sub`。

### 5.8 前端注意事项（第 5 层小结）

1. 结构固定 9 段，但**证据条数、章节正文长度不固定**。
2. 元信息表固定 12 行，键名固定（可用第一列做 key）。
3. 「分析引擎」行 + `> ⚠️` 横幅**必须显示**；`raw` 值要容忍（当前不会出现）。
4. 「涉及设备」可能含 `-`。
5. 聚合指纹是确定性结果但**随数据集变化**，只用于展示。
6. 文件名含 `_`，正文引用要转义/包代码块。
7. 健康报告是另一套模板，别用根因报告的结构去校验它。
8. `<sub>` 落款要放行。

### 6.1 `AlertEvent` 字段表（`notifier/alert.py`）

| 字段 | 类型 | 含义 | 前端怎么用 |
|---|---|---|---|
| `alert_id` | string | 幂等键：`A-<窗口号>-<指纹 sha1 前 8 位>` | 列表 `:key`；同一窗口重算是**同一个 id**（去重靠它） |
| `created_at` | string | 本地时间 `YYYY-MM-DD HH:MM:SS` | 显示"几分钟前" |
| `severity` | string | `P0/P1/P2/P3` | 配色：P0 红 / P1 橙 / P2 黄 / P3 灰 |
| `title` | string | 标题（≤60 字，超长截断加 `…`） | 卡片标题 |
| `summary` | string | **一句话可读摘要**（≤120 字，LLM 优先、规则兜底） | ★ **大字号直接显示，不要自己拼** |
| `window_id` | string | 窗口号，如 `W0014` | 点击跳窗口/报告 |
| `cluster_key` | string | 聚合指纹 `FW-…` / `FEAT-…` | 分组用；**不要当标题显示**（像乱码） |
| `device` | string | 设备描述（**已过滤 `-`**）：`全部 6 个设备` / `设备 A` / `整机` | 副标题 |
| `device_name` | string | 更长的设备说明，如 `全部设备（6 个棚）` | 可选显示 |
| `span` | string | 时间范围 `780s ~ 835s`（设备相对秒） | 副标题；**不是绝对时间** |
| `score` | float | 异常分 0~1（保留 3 位） | 进度条/徽标 |
| `mode` | string | `llm` / `rule` | **必须显示**（与报告引擎标注一致） |
| `source` | string | 数据来源，如 `eval\dataset\d2_v2.log` | 小字标注 |
| `report_file` | string | 关联报告文件名（可能为空串） | 非空时可点击跳 `/api/report` |
| `reasons` | string[] | 触发信号（中文短句，来自窗口打分） | 折叠列表 / "为什么告警" |
| `evidence` | string[] | 证据日志行 `[eid] <原始行>`（最多 6 条） | 折叠显示，等宽字体 |
| `extra` | object | `{lines, err, faults}` 额外统计 | 折叠/调试用 |

> 另外两个**只在 `/api/alerts` 内存态里**才有的字段（由 `AlertManager._remember()` 加上）：
> `delivered`（bool，是否真的推出去了）与 `channels`（每通道结果）、`skip_reason`（被拦原因）。
> **`logs/alerts.jsonl` 里没有这三个字段** —— 它们是 `ev.to_dict()` 直接落盘的。

> **后果**：若前端"邮件预览"用 Markdown 渲染器渲染这段纯文本，`──` 与 `·` 会被吃掉排版；
> 若反过来把报告当纯文本预览，表格会变成一堆竖线。两个预览要分开实现。

### 6.4 Webhook payload（多两个键）

`channels.py` 的 `WebhookChannel` 在 `to_dict()` 基础上加两个字段，**多数机器人免适配即可收**：

```json

  "msgtype": "text"
```

### 6.5 `alert_id` 是确定性的（前端可拿来做幂等）

```python
# alert.py build_alert()
fp = analysis.cluster_key or window.window_id
digest = hashlib.sha1(("%s|%s" % (window.window_id, fp)).encode("utf-8")).hexdigest()[:8]
alert_id = "A-%s-%s" % (window.window_id, digest)
```

* 同一窗口、同一指纹 → **永远同一个 id**，重复推送天然幂等。
* 指纹里含故障码集合，所以**数据/窗口内容变了 id 会变**（这不是 bug，是"内容变了"的正确表达）。
* 健康报告的 id 是 `A-HEALTH-<YYYYmmddHHMMSS>`（时间戳，每次不同）。
* 自测告警的 id 是 `A-TEST-<YYYYmmddHHMMSS>`（`logs/alerts.jsonl` 前 3 行就是）。

真实的三类 id（都来自 `logs/alerts.jsonl`）：

```text
"A-TEST-20261117194817"     ← 通道自测（P3，device="自测（非真实事件）"）
"A-W0014-6aa752ee"          ← 真实异常告警（同一条被推了 5 次，id 完全相同 → 幂等）
"A-HEALTH-20261012132343"   ← 健康报告（格式示例，见 build_health_alert）
```

> ⚠️ **坑**：`logs/alerts.jsonl` 是 **append-only**，同一条告警重复推送会写多行（真实文件里
> `A-W0014-6aa752ee` 出现了 5 次，`created_at` 各不相同）。
> **后果**：前端直接 `map` 这个文件当列表，会出现 5 张一模一样的卡片。
> **做法**：按 `alert_id` 去重，保留最新 `created_at`。

### 6.6 前端注意事项（第 6 层小结）

1. `summary` 是核心内容，直接大字显示；`cluster_key` 是机器键，别当标题。
2. `severity` 四级配色；`mode` 必须显示（llm / rule）。
3. `delivered` / `channels` / `skip_reason` **只在内存态有**，读 JSONL 时要容忍缺失。
4. 去重键用 `alert_id`；同一 id 多行是正常现象（重复推送）。
5. `span` 是设备相对秒，不要显示成日期。
6. 邮件正文是纯文本、报告是 Markdown，两个预览分开做。
