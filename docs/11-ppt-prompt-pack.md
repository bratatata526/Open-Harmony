## 1. 事实底座（每段提示词都会带上它）

> **以下数字全部是实测的，可以直接写进 PPT。**
> 带 ⚠️ 的是"必须照实说"的边界，不能含糊。

### 硬件与数据真实性

- **开发板**：FS-Hi3861（华清远见），Hi3861V100，RISC-V 32 位
- **板载真实传感器**：SHT20（I2C，温湿度）+ AP3216C（I2C，光照/接近/红外）
- **单设备模式**（`FW=v2.3`）：温湿度是 SHT20 **原始读数**，光照是 AP3216C **原始读数**，
  **不加偏置、不加惯性、不加人工噪声** —— 代码里 `is_real` 分支直接 `z->temp_x10 = base_t`
- **六棚模式**：一块板子模拟 6 个大棚。依据是**6 个大棚共享同一片天空**，
  环境参数共模；各棚差异体现为**固定物理偏置 + 热惯性**（朝向/保温/土壤/遮阴）
  - 实测各棚排序 A>C>F>E>D>B，与偏置大小顺序一致
  - 实测 6 个棚变化方向一致率 **76~83%**，而随机数模型只有 ~50%
- ⚠️ **必须照实说**："6 个是**逻辑设备**，不是 6 个物理传感器。
  基准来自真实传感器，偏置是**有物理依据的建模**。"
  **绝对不要说"我们装了 6 个传感器"。**

### 日志规范（`docs/02`，v1.0 冻结）

- 格式：`<秒>.<微秒> <级别> <domain> <tag>: <字段ID> <值> ... z=<zone>`
- **三条真实平台约束**（不是风格偏好）：
  1. `hilog_lite` **不支持 `%s`** → 消息体里禁止字符串值
  2. **单条日志 ≤ 128 字节**，超出**静默丢弃**（不报错不截断）
  3. 最多 6 个数字变参
- 真机实测**最长行 72 字节**（上限 128），有充足余量
- **28 个故障码**（F1001~F5004）+ **25 个错误码**（含 FAQ 第 3 章「系统异常类」：看门狗复位 / 死机 / 非法内存访问 / CPU 过载）
- ⚠️ **平台 printf 有缺陷**：多位数整数会被截断（`1001`→`1`、`-1270`→`-`），
  同一份代码在主机 gcc 上完全正确。**对策：日志路径完全不用 stdio 格式化**，
  自己写十进制转换，并开机自检

### 实测硬指标（可直接上 PPT 数字页）

| 指标 | 实测值 |
|---|---|
| 真机日志解析率 | **100%** |
| 失败行 | 0（复位瞬间的 ROM 引导日志除外，那是正常噪声） |
| 上报周期 | **5.14 秒**（声明 5000ms，比例 1.028） |
| 最长日志行 | 72 字节 / 上限 128 字节 |
| 窗口压缩比 | 313 行 → 2 个异常窗口（**降 99.36%**） |
| 异常识别 | 5 信号加权打分：级别 0.30 / 故障码 0.25 / 静默 0.25 / seq 缺口 0.10 / 阈值 0.10 |
| LLM 报告置信度 | **95%**（真机报告实测） |
| **幻觉率** | **0.00%**（证据编号全部可回查，无效引用被程序层拦截） |
| LLM 成本 | 约 **0.01 元 / 份报告**（2 次调用，模型 `deepseek-flash`） |

### 工程化亮点（答辩加分项，都有实证）

- **14 个真实踩坑记录**（`docs/09`），每个都有症状/根因/解决/验证，例如：
  - 平台 `printf` 截断多位数 → 自写十进制转换
  - **时基错位**：把 10ms/tick 当 1ms，时间戳慢了 10 倍，定时却完全正常（最难发现）
  - 改了源码忘了重烧，现象与"平台 bug"一模一样 → 加开机版本号 + 数值自检行
  - 烧录后必须物理拔插 USB（否则芯片停在 bootloader，连 ROM 日志都不打）
- **防幻觉三重保险**：LLM 只输出证据编号 → 程序校验编号真实性 → 证据段由程序生成
- **聚合与命名分离**：聚合指纹由程序按故障码相似度确定性计算，LLM 只负责起名字。
  （起因是实测发现同一故障被 LLM 命名成中英文两族，导致"智能聚合"失效）
- **降级能力**：LLM 不可用时自动降级到本地规则引擎，报告照出，且报告里**明确标注**降级

```

【坑一：平台 printf 会截断多位数整数】
· 症状：真机上 1001 被打印成 "1"，5001 被打印成 "5"，-1270 被打印成 "-"
· 关键迷惑点：同一份代码在主机 gcc 上【完全正确】——"主机对、板子错"
· 定位：写最小复现，确认是平台 C 库的整数格式化缺陷
· 解决：日志路径完全不用 stdio 格式化，自写十进制转换，输出用 putchar 逐字符
· 附带收获：绕开 stdio 后日志路径开销大幅下降

【坑二：时基错位——定时全对，时间戳慢 10 倍】
· 症状：日志节奏完全正常，但 525 条记录只对应 21 秒设备时间
· 定位方法：拿秒表量——记下设备时间戳，真实等 40 秒，再记一次
  实测真实 40.1 秒 → 设备时间戳只前进 4.1 秒（比例 0.103）
  而每轮循环真实耗时 5.02 秒，与 usleep(5000000) 完全一致
· 根因：SDK 的 tick 频率是 100Hz（10ms/tick），代码却按 1ms 算秒
· 危害（比"时间戳不准"严重得多）：
  60 秒窗口实际切成约 600 秒；静默检测永远不触发；真机数据与评测数据集不同尺度
· 解决：改用 osKernelGetTickFreq() 动态换算，与 SDK 配置解耦

【输出】
· 每个坑用"症状 → 迷惑点 → 定位方法 → 根因 → 解决"五段式
· 重点突出【定位方法】，体现工程能力而不是运气
· 给出这张 PPT 的讲解要点和 100 秒口播稿

### P1-e 智能聚合页

```
为答辩 PPT 写一页"异常智能聚合"，讲清我们的一个【设计缺陷修正】。

【背景】
题目要求"异常智能聚合"，核心是把反复出现的同类异常压成一个族，报告里说"出现 N 次"。

【我们最初的做法】
让 LLM 给异常族命名并作为聚合键（提示词里写"英文下划线命名"）。

【实测发现的问题】
同一批故障在相邻两个 60 秒窗口重复出现：分数一样、行数一样、故障码完全一样，
但 LLM 一次命名成"传感器读取超时"、一次命名成"onewire_sensor_timeout"，
于是"智能聚合"把【同一个族劈成了两类】，还各写了一份报告——聚合要求直接落空。

【修正后的架构】
· 聚合指纹：由【程序】按窗口内故障码集合的 Jaccard 相似度确定性聚类，可复现
· 族名：由 LLM 或故障码字典给出，只负责好听好读
· 好处：换模型、换措辞、LLM 完全挂掉，聚合结果都不变

【实测效果】
修正前：4 个异常窗口 → 劈成 2 个族（名字还不一致）
修正后：4 个异常窗口 → 1 个族，报告写明"本族出现 4 个窗口"

【还要说明一个细节】
指纹不能要求集合完全相等：注入器场景是轮转的，某窗口可能多带一个故障码。
改用 Jaccard 相似度 ≥0.6 聚类，既容得下零星差异，又不会把不相干的问题混进来。

【输出】

## 9. 一页速查：本项目最值得讲的 5 件事

如果 PPT 时间被压缩，只讲这 5 件（按说服力排序）：

1. **数据是真的，而且可当场证明** —— 捂传感器看数值变化，拔线看 OFFLINE
2. **发现了平台 printf 的多位数截断缺陷并绕过** —— "主机对、板子错"的经典案例
3. **发现了时基错位：定时全对、时间戳慢 10 倍** —— 拿秒表量出来的，最隐蔽
4. **防幻觉做到了 0.00%** —— LLM 只出证据编号，证据段由程序生成
5. **自己发现并修正了聚合键的设计缺陷** —— 从"LLM 命名决定聚合"改成"程序算指纹"

> 这 5 件事的共同点：**每一件都有实测数据和文档记录**，不是"我们用了什么技术"，
> 而是"我们发现了什么问题、怎么定位、怎么解决"。这才是工程能力的证明。
